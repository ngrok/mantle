# Charts mount dormant and engage on focus

**Date:** 2026-10-08
**Status:** Accepted
**Scope:** `packages/mantle/src/components/chart/{primitive.tsx,engine.ts,colors.ts,visibility.ts,describe.ts}`, every chart Root (`LineChart`, `BarChart`, `AreaChart`, `ScatterPlot`), `packages/mantle/vitest.setup.ts`, `packages/mantle/src/test-utils/mock-intersection-observer.ts`, `packages/mantle/src/test-utils/engage-chart.ts`
**Amends:** two items of [2026-07-18-canvas-chart-family.md](./2026-07-18-canvas-chart-family.md): "Theme-token colors resolved at runtime via a probe element per chart root", and the sr-only data table in "Interaction is Root's unconditional contract"
**Evidence:** `apps/chart-bench`, 100 line charts of 2 series × 30 points, each 558×314 CSS px, DPR 2, headless Chromium 153 through Playwright, Apple M3 Max, medians of 3 runs. We measured the baseline below on `main` for this change; `apps/chart-bench/REPORT.md` (2026-10-07) holds the comparison with `@tanstack/charts` that prompted the work.

## Context

A dashboard lists charts: one per endpoint, one per domain, one per tenant. The chart family was built for one dense chart, where the engine's decimation keeps a 100,000-point line inside the frame budget, and it was never measured as a list. The bench measured it against `@tanstack/charts`, and the list case was the one mantle lost.

The baseline on `main`, 100 line charts: mount 294 ms, main thread 371 ms, style recalculation 177 ms, and Total Blocking Time 173 ms at 1× CPU; mount 1,192 ms at 4×. Each chart held 171 DOM nodes, 162 of them the sr-only data table and its instructions span, and the 100 canvases held 535 MB of backing store. A reader sees four of those charts.

Two costs made up the mount time.

1. **Color resolution forced 17 style recalculations per chart.** `resolveThroughProbe` appended a `display: none` span to the Root, read `getComputedStyle(probe).color`, and removed it, once per color. Each insertion invalidated the Root's sibling-dependent styles and recalculated the whole chart subtree, table included: 1,704 recalculations for 100 charts, 177 ms at 1× and 765 ms at 4×. Seventeen rather than eight, because the first commit ran before the resize observer delivered, so `#dpr` was still `1`; the resize then changed the color-cache signature, and every color resolved a second time. The tooltip's `ResizeObserver` added one forced layout through its `offsetWidth` read.
2. **Every chart paid its full cost at mount.** Each Root rendered its data table, resolved its colors, measured its axis labels, allocated a 1116 × 628 canvas bitmap, and painted, whether or not a reader could see it.

`content-visibility: auto` on the list's cards cut mount to 85 ms and canvas memory to 120 MB with no library change, which showed where the floor was. It is an app-side fix, and on the Root itself it clips the focus ring and the tooltip, so the component needed its own gate.

## Decision

### 1. Colors resolve from one computed-style read

`createColorResolver` reads `getComputedStyle(root)` once per resolution pass. The computed value of a custom property arrives with every `var()` substituted, and the canvas parses the `oklch()` and `color-mix()` strings mantle's tokens resolve to, so `getPropertyValue("--color-chart-1")` on that one declaration resolves a series color inside the Root's own cascade. A root-scoped `--color-chart-N` override wins exactly as before. A bare `currentColor` resolves from the Root's computed `color`. `canvasParses` checks each candidate against one 1×1 canvas context per document, and only a value the canvas rejects (a nested `var()` left by a fallback, a `currentColor` nested inside another function such as `color-mix()`, `light-dark()`) goes through the probe, which is now one hidden span per Root, mounted once inside the plot box and restyled: the Root's child list is the consumer's, and a `:last-child` rule there must not count a probe. A custom `ReferenceLine` color resolves through the pass's resolver, kept on the color cache, so it adds no read of its own. The constructor seeds `#dpr` so the first pass signs the cache with the real ratio, and the tooltip observer starts when the chart enters view. `observeThemeChanges` shares one `MutationObserver` per document and compares a signature, so a same-value attribute rewrite re-resolves nothing.

### 2. A Root mounts dormant and engages on focus

Every chart Root carries an engagement latch. It starts `false`. It flips to `true` when focus lands anywhere inside the Root: the interaction overlay is the Tab stop, and a focusable part composed inside the Root, such as `CopyButton`, counts too. It never flips back. Visibility never flips it: a chart that scrolls into view paints, and it mounts no table. The Root stamps `data-state="dormant"` then `data-state="engaged"` after the props spread, so a consumer value cannot override it. The sr-only data table mounts on the flip and stays, so a table a screen reader is on never unmounts under its cursor. Focus engages synchronously in the `focus` handler, because the table must exist before the screen reader moves past the overlay, and a discrete event flushes the state update before the next key arrives. A decorative chart renders no table and carries no `data-state`: it has no overlay, so focus can never engage it. It paints on the same visibility gate.

The table follows focus and not visibility because of the list page. It renders a sparkline chart in every table cell, two per row, forty in view at once. A table that mounted on visibility would add thousands of nodes nobody asked for (a 30-row table is about 160 nodes, and forty of them are over 6,000), and a screen reader navigating that list would meet a nested table inside every cell. The always-rendered description (§4) names the kind, the count, the x range, and the series; Tab into a chart gives the full table; the keyboard point cursor reads every value.

### 3. A dormant Root is a shell; the engine and its layers arrive at activation, outside React

`visibility.ts` holds one trio of `IntersectionObserver`s per document: a `visible` band at the viewport, a `near` band at `rootMargin: 100%`, and a `far` band at `300%`, all with `scrollMargin`, so a chart inside a scrolling panel paints when it nears the panel's clip rather than when the panel reveals it. A percentage margin resolves against the root's own height for top and bottom and its width for left and right (checked in Chromium, Firefox, and WebKit on 2026-10-10), so `100%` is one viewport in each direction. On an engine without `scrollMargin` (probed once), a chart inside a scrolling panel observes the `near` and `far` bands from the panel, and the panel itself observes the same bands from the viewport: a band observes the panel's charts only while the panel is inside it, so a panel below the fold activates nothing and a panel that scrolls away releases its charts. The `visible` band observes from the viewport on every engine. The `near` band drives `engine.setInView`; the `visible` band drives `engine.markSeen`; leaving the `far` band calls `engine.releaseBackingStores`, which zeroes the canvas and the marks layer and marks the chart for a full repaint on return. A dormant Root renders a shell: the wrapper, the plot box, the interaction overlay, the sr-only description, and the live region. It holds no canvas, no hover layers, no tooltip surface, and no engine. `activate` (a function the Root keeps in a ref) builds the canvas and the three layers with `createChartLayers`, inserts them into the plot (the canvas first, the layers last), constructs the engine with the plot rect the intersection entry carried (`size`), pushes the inputs the Root has collected (`inputsRef`: options, rows, callbacks, the controlled index), ingests, and calls `engine.commitNow()`, so the chart paints in the task that activated it. React never re-renders for activation: a React-state activation measured net slower than the always-mounted engine on the visible set (40 sparklines: 13.6 ms of render and layout effects plus a 13.5 ms frame for the 200 inserted nodes, then the paint frame), because the commit, the style recalc, and the layout each ran once more. The engine is constructed with `inView: false` and then told `setInView(near)` and, when the `visible` band already reported, `markSeen()`, so the enter reveal still holds at zero until the chart is on screen.

The `near` band queues the activation (`activation.ts`) instead of running it: one delivery can name forty charts, and forty activations in one task are 12 ms at 1× and about 50 ms at 4×. `flushActivations` runs after each delivery's loop: it sorts the queue on-screen first (the entry's `boundingClientRect` against the viewport) and then by document order, runs activations until 4 ms have passed, and continues after `scheduler.yield()` (a message-channel hop where it is missing). A later `visible` report promotes a queued chart; a Root's cleanup cancels its entry. The first slice runs inside the observer task, so under the synchronous happy-dom stub a chart activates inside its own layout effect and every test that queried the canvas at mount still does.

Focus and print activate synchronously and bypass the queue: the `focus` handler calls `activate` after it sets the engaged latch and holds the chart in view while it has focus (a chart focused with `preventScroll` paints offscreen); `blur` hands the gate back to the observer's last `near` report and releases the canvas when the last `far` report left the chart beyond the band, and every Root holds one entry in the shared `beforeprint` listener that calls `activate` and then `engine.paintForPrint()` (idempotent within one print, so the engine's own listener is a no-op). `afterprint` releases the ones out of view. The tooltip surface stays React-rendered for the consumer's render prop and `divProps`; the Root mounts it on the store's `hoverEver` latch (set by the first `publishHover`) through a callback ref that hands the element to `engine.attachTooltip`, and keeps it. A chart nobody points at holds no surface. An engine's `#commit` runs layout once per data or size change (never per hover frame) and skips color resolution, text measurement, and paint while out of view; a chart with no axis and no grid measures no tick text at all. A dormant engine holds settled state: every tween jumps instead of gliding, so entry paints the current data at once. The reduced-motion query, the device-pixel-ratio watcher, and the print listener pair live once per window (`environment.ts`); the canvas parse verdict of every color value lives once per document. A dormant Root throws the `dataKey`, `xKey`, and `zKey` invariants in its own mount commit through `assertChartKeys`, with the messages the engine's ingest throws and against the rows the engine plots (on a continuous scale, those with a finite x), so a typo fails where it did before and not in the observer task.

### 4. A described overlay replaces the instructions span

The overlay's `aria-describedby` points at one always-rendered sr-only span, `data-slot="<kind>-description"`, whose text is what `describeChart` composes: the chart kind, the number of data points (categories on a bar chart), the x range from first to last (`at X` for one point), the series labels, and then the unchanged keyboard instructions. A dormant chart has no table, so this sentence is what a screen reader gets from it. The span holds three child spans: React renders the sentence and the instructions, and the Root writes the series sentence into the middle span with `textContent` from a store subscription, because the parts register after the Root's first render and a re-render for them changed every description's text after the first layout (100 line charts paid 5 ms of passive effects and a 7 ms second layout for it, and a subscription also follows a part that registers without a Root render). Three element children keep a browser translation engine away from the text nodes. The span stays `sr-only`, not `hidden`: a hidden span would shape no text (200 descriptions of forty words cost about 4 ms of shaping in the first layout of the sparkline table, measured 2026-10-08), but a screen reader's virtual cursor would no longer meet the description as page content. Cody kept the reading order over the milliseconds. Server HTML carries the plain count alone. The range waits for hydration, because `Intl` output differs by locale.

### 5. The live region stays

The polite `role="status"` region mounts with the Root, as before. A region inserted right before its first message is not announced.

### 6. The test contract

`packages/mantle/vitest.setup.ts` installs `createIntersectionObserverStub({ intersecting: true }).Observer` as the global under happy-dom, by direct assignment, because `unstubGlobals` would undo a `vi.stubGlobal` there before the first test. The stub delivers inside `observe()`, and the activation queue runs its first slice inside the delivery, so every happy-dom chart test sees an activated chart at mount (canvas and layers in the plot), as it did before, no tooltip surface until a hover or a keyboard step, and no table until it focuses the chart. `engageChart()` in `packages/mantle/src/test-utils/engage-chart.ts` focuses the overlay inside `act`; a consumer suite does the same with `await user.tab()` or `element.focus()` inside `act`, then `findByRole("table")`. A test that needs an unpainted chart stubs its own observer with `intersecting: false` and drives `enter` and `leave`. jsdom has no `IntersectionObserver`, so `observeChartVisibility` reports both bands in view at once, and a chart there paints at mount. The browser project keeps Chromium's observer.

## Consequences

- **Measured result (2026-10-08, same bench, medians of 3, `animate={false}`):** 100 line charts mount in 64 ms at 1× (from 294) with 119 ms of main-thread time (from 371), 4 ms of style recalculation (from 177), Total Blocking Time 0 (from 173), and a worst frame of 17 ms (from 250); at 4× they mount in 194 ms (from 1,192) with TBT 39 ms (from 980). The page holds 1,393 DOM nodes (from 17,135), 14 per dormant chart, and 158 MB of canvas memory after a full scroll (from 535). One chart alone mounts in 53 ms and ten in 58 ms, so the 99 extra charts cost 12 ms of mount and 37 ms of main-thread time. 100 bar charts: 60 ms at 1× (from 153), 177 ms at 4× (from 658). A table of 100 rows with two 112×24 sparklines each (200 charts): 89 ms at 1× (from 207) with TBT 0 (from 73) and 3,170 DOM nodes (from 10,126); 369 ms at 4× (from 829) with TBT 153 ms (from 635). The target was mount near 50 ms at 1×, TBT 0, about 11 DOM nodes per dormant chart, and canvas memory for the visible charts alone.
- **One accepted regression:** a screen reader's table list (quick navigation by table) names only the charts a reader has focused. A reader who tabs to a chart engages it; a reader who scrolls past it, or who lists tables before tabbing to any, sees fewer tables than the page holds. The description on every overlay names what each chart holds, focused or not.
- **A `minor` bump.** A test that queries the table at mount and an agent that reads it from the DOM both depend on a documented behavior that changed. The changeset carries the migration: focus the chart (`user.tab()`, or `element.focus()` inside `act`) and then query the table in a test; focus and wait for `data-state="engaged"`, or use `CopyButton`, for an agent.
- **`content-visibility: auto` is a complement, not a substitute.** The docs recommend it on list cards: it skips style and layout for offscreen cards, and the chart's gate already skips paint and canvas memory.
- `data-state` and `<kind>-description` are public API on every interactive Root, documented in the JSDoc and in the four API references.

## Alternatives rejected

- **A page-level color cache** keyed by theme signature: it cannot see a root-scoped `--color-chart-N` override, which the docs promise. The per-document cache that did land holds only the canvas parse verdict per value string, which no override changes.
- **Activation through React state** (`setActive(true)` in the observer callback): measured net slower than the always-mounted engine on the visible charts, because the commit, the style recalc, and the layout each ran once more; see §3.
- **A lazy engine with no mount-time validation:** a `dataKey` typo would throw in the observer task, outside any error boundary. `assertChartKeys` keeps the throw in the mount commit.
- **`content-visibility: auto` on the Root:** paint containment clips the focus ring and the tooltip, which overflow the Root.
- **Mounting the table on visibility,** with the paint gate: a list page renders a sparkline in every table cell, two per row, forty in view at once, so the tables nobody asked for add thousands of nodes, and a screen reader navigating the list meets a nested table inside every cell. The description names what each chart holds, Tab gives the table, and the point cursor reads every value.
- **An `innerHTML` twin** written outside React: it keeps the node count, which is the cost.
- **A shared instructions element** for every chart on the page: the description is per chart (its kind, count, range, and series), so a shared element could carry only the keyboard sentence, it saves one node of 171, and it needs a page-level owner that a self-contained Root does not have.
- **Lazy engine construction** on engagement: it saves about 0.2 ms per chart and loses the fail-fast invariants at mount.
- **A lazy live region** mounted on engagement: a region inserted right before its first message is not announced.
- **The persistent-probe fix alone** (`bench/probe-fix.patch`): it halves mount time but still forces one recalculation per color, because restyling the probe recalculates that span.

## Deferred (named, with the trigger that reopens each)

- **Idle mounting of every table**, so a page eventually holds every twin. Reopen if a scraper needs every table without focusing each chart.
- **`hidden` description spans** in place of `sr-only`. An `aria-describedby` target contributes its text while hidden (accname step 2A), so the overlay's description would survive, and the first layout of a 200-sparkline table would drop about 4 ms of text shaping. Rejected on 2026-10-10: browse mode would stop reading the description as page content. Reopen only if browse-mode duplication is reported.
- **A shared live region** in place of one `role="status"` span per chart. Reopen if the per-chart span shows up in a profile; today it is one empty element.
- **Engine and store micro-wins the review priced at 0.3–4 ms each on 40 visible sparklines:** rebuild the store snapshot lazily on read instead of once per part registration (6 rebuilds per line chart), create the hover layers on the first hover with the tooltip, insert the canvas at its bitmap size from the entry rect, share tick generation and label measurement across charts with one scale and domain, and write overlay opacities only when the hover state changes. Reopen when the activation slice of a 40-chart page exceeds its 4 ms budget at 1× on the bench.
- **Fewer fibers per dormant shell.** The shell is one Root fiber, its context provider, four host nodes, and the composed parts; 100 shells render in about 13 ms of React at 1×, and only an app-level deferral (`startTransition`, virtualization) takes that off the first commit. Reopen if a list page needs the first commit under one frame with 100 charts in it.
