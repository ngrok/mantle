<PageHeader id="sidebar">Sidebar</PageHeader>

A composable, collapsible app-navigation sidebar. `Sidebar.Root` owns the state and renders no DOM;
`Sidebar.Nav` renders the panel — inline on desktop, collapsing to a skinny
[icon rail](#collapsing-to-the-icon-rail), and a left-side [Sheet](/components/overlays/sheet) below the
root's `mobileBreakpoint`; and `Sidebar.Trigger` toggles it from anywhere under the root, which is what
keeps the sidebar decoupled from your app shell: place the trigger in an
[App Layout](/layouts/app-layout) header without the shell knowing the sidebar exists.

The sidebar is routing-agnostic. Compose router links with `asChild` on `Sidebar.ItemButton` and drive
`current` from your router's location. The demo below runs in its own framed document, exactly like a real
app: switch the preview to the mobile viewport to see the sheet presentation, use the trigger in the header
to collapse and expand the panel, open the product switcher at the top of the sidebar to choose a product
from a centered [Dialog](/components/overlays/dialog), and toggle the notice to see the shell's full-window
[`AppLayout.Notice`](/layouts/app-layout) strip push everything — sidebar included — down.

`Sidebar.Footer` holds the panel's stable rows, bottom-anchored under the scrolling body: the
account-scoped destinations every product shares, a **Help** row, a `Sidebar.Separator`, and the
account switcher. The Help row and the switcher row are ordinary sidebar rows composed with
`DropdownMenu.Trigger asChild`, so each keeps the panel's row treatment, stays highlighted while its menu is
open, and opens the menu upward (`side="top"`) — the footer sits at the bottom of the viewport, so downward
is off-screen. The switcher's one menu covers both scopes it names: account destinations and switching, then
user-level items including a **Theme** submenu — mantle's
[`ThemeDropdownMenuRadioGroup`](/components/forms/theme-switcher) exists for exactly that spot.

Choosing **Account settings** from that menu shows a second **section** of navigation in the same
sidebar: the header's switcher becomes a back link, `Sidebar.Body` renders the settings groups, and the
`<nav>` landmark renames itself from `Main` to `Settings`. That is composition, not a feature — the sidebar
never knows which section it is showing; the app derives it from the route and renders different children.
The footer does not move while that happens.
Click into the frame and press <kbd>⌘B</kbd>/<kbd>Ctrl+B</kbd> — the shortcut binds to the frame's own
window, not this page. The demo narrows `mobileBreakpoint` to `md` so the desktop panel survives the
preview's desktop and tablet widths; ngrok's dashboards keep the `lg` default.

```tsx
// ArrowDown/ArrowUp wrap around the product cards, Home/End jump to the edges;
// Enter and Space activate the focused card natively.
function handleProductOptionKeyDown(event: KeyboardEvent<HTMLButtonElement>) {
	const container = event.currentTarget.closest("[data-product-options]");
	if (container == null) {
		return;
	}
	const options = Array.from(container.querySelectorAll("button"));
	const focusedIndex = options.findIndex((option) => option === event.currentTarget);
	if (focusedIndex === -1) {
		return;
	}
	const lastIndex = options.length - 1;
	if (event.key === "ArrowDown") {
		event.preventDefault();
		options[focusedIndex === lastIndex ? 0 : focusedIndex + 1]?.focus();
	} else if (event.key === "ArrowUp") {
		event.preventDefault();
		options[focusedIndex === 0 ? lastIndex : focusedIndex - 1]?.focus();
	} else if (event.key === "Home") {
		event.preventDefault();
		options[0]?.focus();
	} else if (event.key === "End") {
		event.preventDefault();
		options[lastIndex]?.focus();
	}
}

/**
 * The product switcher in the sidebar header: a `Sidebar.SwitcherTrigger`
 * trigger that opens a centered product-choice dialog. The current product's

function ProductSwitcherDialog({
	onProductChange,
	productId,
}: {
	onProductChange: (productId: string) => void;
	productId: string;
}) {
	const currentOptionRef = useRef<HTMLButtonElement | null>(null);
	const product = products.find((candidate) => candidate.id === productId) ?? products[0];

	return (
		<Dialog.Root>
			<Dialog.Trigger asChild>
				<Sidebar.SwitcherTrigger>
					<ProductIcon product={product} />
					<span className="text-strong min-w-0 flex-1 truncate text-base">{product.label}</span>
					{/* the double caret reads "pick one of several"; a caret-down would
					    promise a menu dropping from the row, and this trigger opens a dialog */}
					<CaretUpDownIcon className="text-muted size-4 shrink-0" />
				</Sidebar.SwitcherTrigger>
			</Dialog.Trigger>
			<Dialog.Content
				className="bg-popover"
				preferredWidth="max-w-xl"
				onOpenAutoFocus={(event) => {
					// land focus on the current product's card, not the first card
					event.preventDefault();
					currentOptionRef.current?.focus();
				}}
			>
				<Dialog.Body className="p-6">
					<Dialog.Title className="text-strong text-center text-lg font-medium">
						Choose a product
					</Dialog.Title>
					<div className="mt-6 flex flex-col gap-2" data-product-options="">
						{products.map((candidate) => {
							const isCurrent = candidate.id === productId;
							return (
								<Dialog.Close key={candidate.id} asChild>
									<button
										ref={isCurrent ? currentOptionRef : undefined}
										type="button"
										className={cx(
											"group border-card-muted bg-card flex w-full flex-col rounded-lg border p-4 text-left shadow-sm transition-none focus:outline-hidden focus-visible:ring-4",
											candidate.cardHoverClassName,
											isCurrent && candidate.cardCurrentClassName,
										)}
										onClick={() => onProductChange(candidate.id)}
										onKeyDown={handleProductOptionKeyDown}
									>
										<span className="flex w-full min-w-0 items-center justify-between gap-3">
											<span className="flex min-w-0 items-center gap-3">
												<ProductIcon className="size-7" product={candidate} />
												<span
													className={cx("truncate text-sm font-medium", candidate.textClassName)}
												>
													{candidate.label}
												</span>
											</span>
											<ArrowRightIcon

													"text-muted size-5 shrink-0",

// The navigation for whichever section is showing — a product's pages or the
// settings pages. The sidebar never knows which: the app picks the sections.
function SectionNav({
	pathname,
	onNavigate,
	sections,
}: {
	pathname: string;
	onNavigate: (path: string) => void;
	sections: Array<NavSection>;
}) {
	// Inside Sidebar.Root, useSidebar closes the mobile sheet on navigation.
	const { setOpenMobile } = useSidebar();

	return (
		<>
			{sections.map((section) => (
				<Sidebar.Group key={section.title ?? "top-level"}>
					{section.title != null && <Sidebar.GroupLabel>{section.title}</Sidebar.GroupLabel>}
					<Sidebar.List>
						{section.items.map((item) => (
							<Sidebar.Item key={item.path}>
								<Sidebar.ItemButton asChild current={pathname === item.path}>
									<a
										href={item.path}
										onClick={(event) => {
											event.preventDefault();
											onNavigate(item.path);
											setOpenMobile(false);
										}}
									>
										{item.icon}
										{item.label}
									</a>
								</Sidebar.ItemButton>
							</Sidebar.Item>
						))}
					</Sidebar.List>
				</Sidebar.Group>
			))}
		</>
	);
}

export function AppShell() {
	// the framed examples fake a router so they can be embedded; a real app
	// renders react-router `Link`s through `asChild` and reads `useLocation()`
	const [pathname, setPathname] = useState("/endpoints");
	// where the settings section's back link goes: the product route the reader
	// left. A real app reads this from router history (or a fixed section parent).
	const [returnPath, setReturnPath] = useState("/endpoints");
	const [productId, setProductId] = useState("universal-gateway");
	const [accountId, setAccountId] = useState("acc_acme");
	const [showNotice, setShowNotice] = useState(false);

	const inSettings = isSettingsPath(pathname);
	const productItems = [...navSections.flatMap((section) => section.items), ...footerItems];
	const currentItem = [
		...productItems,
		...settingsSections.flatMap((section) => section.items),
	].find((item) => item.path === pathname);
	const returnLabel =
		productItems.find((item) => item.path === returnPath)?.label ?? "the dashboard";

	// every navigation goes through here, so entering the settings section always
	// records the product page its back link returns to
	function navigate(path: string) {
		if (isSettingsPath(path) && !inSettings) {
			setReturnPath(pathname);
		}
		setPathname(path);
	}

	return (
		// the framed demo narrows the mobile breakpoint; most apps keep the "lg" default
		<Sidebar.Root mobileBreakpoint="md">
			<AppLayout.Root className="fixed inset-0">
				<SkipToMainLink />
				<AppLayout.Notice>
					{showNotice && (
						<div className="text-on-filled flex items-center gap-2 bg-red-600 px-4 py-1 text-xs">
							<WarningCircleIcon weight="fill" className="shrink-0" />
							Scheduled maintenance in progress — the dashboard is read-only.
						</div>
					)}
				</AppLayout.Notice>
				<AppLayout.Workspace>
					{/* the landmark is renamed with the section it is showing */}
					<Sidebar.Nav aria-label={inSettings ? "Settings" : "Main"}>
						<Sidebar.Header>
							{inSettings ? (
								<SettingsHeader
									returnLabel={returnLabel}
									returnPath={returnPath}
									onBack={() => setPathname(returnPath)}
								/>
							) : (
								<ProductSwitcherDialog productId={productId} onProductChange={setProductId} />
							)}
						</Sidebar.Header>

						<Sidebar.Body>
							<SectionNav
								sections={inSettings ? settingsSections : navSections}
								pathname={pathname}
								onNavigate={navigate}
							/>
						</Sidebar.Body>

						{/* the footer is the panel's stable region: bottom-anchored under the
						    scrolling body, and unchanged by what the body is showing */}
						<Sidebar.Footer>
							{footerItems.map((item) => (
								<Sidebar.ItemButton key={item.path} asChild current={pathname === item.path}>
									<a
										href={item.path}
										onClick={(event) => {
											event.preventDefault();
											navigate(item.path);
```

## Composition

Compose the parts of a `Sidebar` together to build your own:

```text showLineNumbers=false
Sidebar.Root
├── Sidebar.Nav
│   ├── Sidebar.Header
│   │   └── Sidebar.SwitcherTrigger
│   ├── Sidebar.Body
│   │   ├── Sidebar.SearchTrigger
│   │   └── Sidebar.Group
│   │       ├── Sidebar.GroupLabel
│   │       └── Sidebar.List
│   │           └── Sidebar.Item
│   │               └── Sidebar.Tooltip
│   │                   └── Sidebar.ItemButton
│   └── Sidebar.Footer
│       ├── Sidebar.ItemButton
│       ├── Sidebar.Separator
│       └── Sidebar.SwitcherTrigger
└── Sidebar.Trigger
```

`Sidebar.Root` renders no DOM — it only carries state, so `Sidebar.Trigger` can live anywhere under it,
including inside layout components that know nothing about the sidebar. Render exactly one `Sidebar.Nav` per
`Sidebar.Root`; nested roots shadow the outer sidebar for everything below them.
There is deliberately no account-switcher part: a "Switch accounts" submenu is a composition of
[DropdownMenu](/components/overlays/dropdown-menu)'s `RadioGroup`/`RadioItem` with
[Avatar](/components/data-display/avatar), exactly as the shell demo above shows — the account model (what a
row contains, badges, ordering) belongs to the app, not the design system.

## Polymorphism

`Sidebar.Header`, `Sidebar.Body`, `Sidebar.Footer`, `Sidebar.Group`, `Sidebar.GroupLabel`, `Sidebar.List`,
`Sidebar.Item`, `Sidebar.ItemButton`, `Sidebar.SwitcherTrigger`, `Sidebar.Separator`, and `Sidebar.Tooltip`
accept an `asChild` prop. When `true`, the part renders its single child instead of its default element,
forwarding all class names, `data-*` attributes, and the ref onto that child. The most common uses are router
links on `Sidebar.ItemButton` (shown throughout this page) and composing `Sidebar.SwitcherTrigger` with
`DropdownMenu.Trigger asChild` or `Dialog.Trigger asChild`. `Sidebar.Separator` inherits it from the
[Separator](/components/structure/separator) it composes, and `Sidebar.Tooltip` forwards it to the
[`Tooltip.Content`](/components/overlays/tooltip#tooltipcontent) whose props it takes — Radix implements that
swap itself, so it replaces the **tooltip surface**, not the row you wrap. The row's own polymorphism goes
through the `Sidebar.ItemButton` or `Sidebar.SwitcherTrigger` inside it.

`Sidebar.Root`, `Sidebar.Nav`, and `Sidebar.Trigger` are the exceptions. `Sidebar.Root` renders no DOM at
all, so there is nothing to swap; the nav renders a fixed two-element collapse structure (and a `Sheet` on
mobile); and the trigger renders a fully-wired control — build custom triggers with `useSidebar` instead.

Below, `Sidebar.GroupLabel` renders a real `<h3>` and each `Sidebar.ItemButton` renders an `<a>` instead of
its default `<button>`. The parts' classes, `data-*` state, and refs land on your elements, and the
group's `aria-labelledby` wiring still names the list — inspect the rendered markup to see it.

### With react-router

The example above fakes a router so this page stays self-contained. With react-router, render a `NavLink` and
let it own the active state — **this is the whole integration**.

The two snippets in this section are the only ones on this page with nothing running above them, and
deliberately so: this documentation site is itself a react-router app, react-router permits exactly one
router per tree, and a live `NavLink` here would resolve against the docs site's own URLs and navigate the
reader off the page on click. That is also why every other example on this page fakes a router. Both snippets
are complete components — copy either one straight into a real app, where its `NavLink`s resolve against your
routes:

```tsx
import { Sidebar } from "@ngrok/mantle/sidebar";
import { GlobeHemisphereWestIcon } from "@phosphor-icons/react/GlobeHemisphereWest";

	return (
		<Sidebar.Group>
			<Sidebar.GroupLabel>Traffic</Sidebar.GroupLabel>
			<Sidebar.List>
				<Sidebar.Item>

						<NavLink to="/endpoints">
							<GraphIcon />
							Endpoints
						</NavLink>
					</Sidebar.ItemButton>
				</Sidebar.Item>
				<Sidebar.Item>
					<Sidebar.ItemButton asChild>
						<NavLink to="/domains">
							<GlobeHemisphereWestIcon />
							Domains
						</NavLink>
					</Sidebar.ItemButton>
				</Sidebar.Item>
			</Sidebar.List>

```

No `current`, no `useMatch`, no `className` — the row highlights itself. `NavLink` already resolved the match
and sets `aria-current="page"`, and the current-row treatment follows **either** `aria-current="page"` or
`data-current`, so the router's own answer drives mantle's own styling. Pass `current` for the rows whose
parent knows (a plain `Link`, a custom matcher, a row that is current for a reason the URL doesn't express).

Reach for `NavLink`'s render-prop `className` only to add styling of your own on top —
`Sidebar.ItemButton`'s `asChild` composes it rather than dropping it, at the usual child-wins precedence (see
[Slot → Render props on the child](/components/primitives/slot#render-props-on-the-child)):


## Width

The panel's width is a CSS variable, not a prop: `Sidebar.Nav` reads each of the three widths with the
default as its fallback (`w-(--sidebar-width,16rem)`), so there is nothing to thread through your shell
and one place to change it.

| CSS Variable             | Default          | What it sizes                                           |
| ------------------------ | ---------------- | ------------------------------------------------------- |
| `--sidebar-width`        | `16rem` (256px)  | The expanded desktop panel                              |
| `--sidebar-width-icon`   | `3.25rem` (52px) | The [collapsed icon rail](#collapsing-to-the-icon-rail) |
| `--sidebar-width-mobile` | `18rem` (288px)  | The mobile `Sheet` panel                                |

Override one sidebar by setting the variable on `Sidebar.Nav` — a Tailwind arbitrary property is the
shortest route, and `cx` keeps it deterministic. The panel below is `18rem` wide expanded; collapse it with
the trigger and the rail still uses the default `--sidebar-width-icon`:

Override every sidebar in your app from your global stylesheet. Custom properties inherit, and the parts

```css

	--sidebar-width-mobile: 20rem;

```

Three consequences of that inheritance direction worth knowing: setting a width on something the panel
_contains_ does nothing (values flow parent → child, never child → parent); `AppLayout` never needs to
know the number — the `AppLayout.Content` card takes the remaining row space, so a wider sidebar
narrows the card by construction; and a surface that renders _outside_ the panel — a switcher's menu, portaled to
`document.body` — inherits none of them, which is what
[`--sidebar-row-width`](#sizing-a-menu-to-a-sidebar-row) exists for.

## Collapsing to the icon rail

On desktop the panel collapses to a skinny icon rail that keeps every row's leading icon visible and
clickable: each row becomes a square chip around its icon, group labels fade out in place — their rows are
retained, so icon groups stay visually separated and every icon keeps the exact position it has when
expanded — the switcher rows in the header and footer collapse to their leading visual (product icon,
account avatar), and the rail keeps the same `bg-base` surface as the expanded panel — no border, no
separate chrome. The rail width is the `--sidebar-width-icon` CSS variable (default `3.25rem`) — see
[Width](#width).

Everything in the icon rail stays in the tab order and the accessibility tree — labels are clipped or
visually hidden, not removed — so screen readers announce the full row names and lists keep their group
names. The scrollable `Sidebar.Body` always fades its overflowing edges; in the collapsed rail it also
hides its scrollbar and relies on the fade alone. Collapse and expand the shell demo at the top of this page
with its header trigger or <kbd>⌘B</kbd>/<kbd>Ctrl+B</kbd> (click into the frame first — the shortcut binds
to the frame's own window).

## Sizing a menu to a sidebar row

A menu opened from a sidebar row should be as wide as the row it opens from, and
[`DropdownMenu.Content`](/components/overlays/dropdown-menu#dropdownmenucontent)'s `width="trigger"` does
exactly that — until the panel collapses to the icon rail, where the trigger is a 36px chip (28px for a
`Sidebar.ItemButton` row) and the menu shrinks with it. The menu cannot solve this from the sidebar's
variables either: it renders in a portal on `document.body`, so it inherits nothing the panel sets.

`mantle.css` declares the row width at `:root` for this, derived from the panel width:

| CSS Variable          | Default | Description                                                                                                                                                                 |
| --------------------- | ------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `--sidebar-row-width` | `15rem` | One row's width inside the expanded panel (240px): `calc(var(--sidebar-width, 16rem) - 1rem)`, the panel width minus the gutter `Sidebar.Header`/`Body`/`Footer` all apply. |

Keep `width="trigger"` and floor the menu at it. The switcher row below is a collapsed chip; open its menu,
expand the panel with the trigger, and open it again — the menu is the same width both times:

## Navigation anatomy

The navigation parts are plain styled elements: `Sidebar.Group` pairs an optional muted `Sidebar.GroupLabel`
with a `Sidebar.List` of rows, and links the two with `aria-labelledby` automatically so each list is
announced with its group's name. `Sidebar.ItemButton` renders a leading icon slot and a truncating label, and
`current` sets both `aria-current="page"` and the `data-current` visual state — the row's current treatment
follows either one, so a composed child that marks itself (react-router's `NavLink`) needs no `current` at all.

> [!IMPORTANT]
> **The navigation is one level deep.** There is no nested item and no collapsible group — a
> `Sidebar.List` holds rows, not sub-lists. A two-level nav cannot be lifted and shifted onto this component;
> it has to flatten into `Sidebar.GroupLabel` + rows, which also means every row that was previously a
> second-level text link now needs a leading icon (the collapsed rail is icon-only, so a row without one
> becomes a blank chip). Budget for that before you start: it is usually the largest single chunk of a
> migration, and it is a design decision, not a mechanical one.

> This is deliberate — a disclosure tree is a different ARIA pattern with its own keyboard contract, and
> nesting it inside a rail that collapses to icons has no coherent collapsed presentation. If you genuinely
> need a tree, compose one from [Accordion](/components/data-display/accordion) inside `Sidebar.Body` rather than
> expecting the rail to collapse it.

## The search row

`Sidebar.SearchTrigger` is the row that opens a search or command palette. It is deliberately a navigation row
and not a text field: the chrome is a `Sidebar.ItemButton`'s, down to the 28px chip it becomes in the collapsed
rail, because a search entry point in a sidebar is one of the rows rather than a form control wedged among
them. Its `shortcut` hint appears on hover or keyboard focus and is otherwise invisible, so the resting panel
stays quiet.

The row is styling only. Wrap it in
[`Command.SearchTrigger`](/components/navigation/command#commandsearchtrigger) for the dialog wiring,
`aria-keyshortcuts`, and the behavior that makes typing or pasting into the row open the palette with that text
already in the query — and in `Sidebar.Tooltip` so the row keeps a visible label once the panel collapses.

`Sidebar.Body` is the default home — above the first `Sidebar.Group`, in the same column as the navigation
rows. Put the row in [`Sidebar.Header`](#sidebarheader) instead when it has to stay put while the navigation
scrolls: the switcher keeps the header's alignment band, the search row takes its own row below, and the
[`AppLayout.Header`](/layouts/app-layout#applayoutheader) toolbar keeps matching the switcher row alone. The
header reserves no scrollbar gutter, so on a platform whose scrollbars take space a row there runs wider than
the rows inside `Sidebar.Body`.

Collapse the panel to watch the row join the icon column, or press `⌘K` inside the preview.

## Persisting the collapsed state

`Sidebar.Root` supports both uncontrolled (`defaultOpen`) and controlled (`open` + `onOpenChange`) desktop
state, and the mobile sheet mirrors that with `openMobile` + `onOpenMobileChange`. To persist the collapsed
state across visits, use the **fully controlled** form with
[`useLocalStorage`](/hooks#uselocalstorage):

> [!IMPORTANT]
> With **storage-backed** persistence in an SSR app, `defaultOpen` does not work: the uncontrolled state
> initializes exactly once at the hydration render, before the stored value is available, so controlled
> `open` is the reliable form. This does **not** apply to the cookie recipe below — a cookie is available
> to the server, so `defaultOpen` is correct there.

This recipe is SSR-safe: [`useLocalStorage`](/hooks#uselocalstorage) is `useSyncExternalStore`-backed with a
server snapshot, so the server render and the hydration render agree (no hydration mismatch), and the
sidebar deliberately suppresses its collapse transition until after hydration, so a persisted-collapsed
sidebar **snaps** shut instead of animating on page load. What no localStorage recipe can do is affect the
server-rendered HTML itself — a persisted-collapsed sidebar paints expanded for one frame before the
post-hydration correction. If that frame matters, [persist to a **cookie**](#persisting-to-a-cookie-ssr)
instead, the same way the theme system solves FOUC server-side.

### Persisting to a cookie (SSR)

A cookie is the only storage the **server** can read, so it is the only way to render the collapsed state
into the initial HTML with no first-frame correction at all. `@ngrok/mantle/sidebar` ships the pair for it,
mirroring [`extractThemeCookie`](/components/primitives/theme#extractthemecookie).

This is the one recipe on this page with no live preview above it, because the thing being demonstrated is a
**server** render: the value has to arrive from a loader, in the initial HTML, before any of this page's
JavaScript runs. Here is the whole route module — a react-router 7 root, complete as written:

```tsx
// app/root.tsx
import { AppLayout } from "@ngrok/mantle/app-layout";
import { Main } from "@ngrok/mantle/main";
import {
	extractSidebarStateCookie,
	serializeSidebarStateCookie,
	Sidebar,
} from "@ngrok/mantle/sidebar";
import { SkipToMainLink } from "@ngrok/mantle/skip-to-main-link";
import { GraphIcon } from "@phosphor-icons/react/Graph";
import { NavLink, Outlet } from "react-router";
import type { Route } from "./+types/root";

export const loader = ({ request }: Route.LoaderArgs) => ({
	// `undefined` means "no preference yet" — pick your own default here
	sidebarOpen: extractSidebarStateCookie(request.headers.get("Cookie")) ?? true,
});

export default function Root({ loaderData }: Route.ComponentProps) {
	return (
		<Sidebar.Root
			defaultOpen={loaderData.sidebarOpen}
			onOpenChange={(open) => {
				document.cookie = serializeSidebarStateCookie(open);
			}}
		>
			<AppLayout.Root className="fixed inset-0">
				<SkipToMainLink />
				<AppLayout.Workspace>
					<Sidebar.Nav aria-label="Main">
						<Sidebar.Body>
							<Sidebar.Group>
								<Sidebar.GroupLabel>Traffic</Sidebar.GroupLabel>
								<Sidebar.List>
									<Sidebar.Item>
										<Sidebar.ItemButton asChild>
											<NavLink to="/endpoints">
												<GraphIcon />
												Endpoints
											</NavLink>
										</Sidebar.ItemButton>
									</Sidebar.Item>
								</Sidebar.List>
							</Sidebar.Group>
						</Sidebar.Body>
					</Sidebar.Nav>
					<AppLayout.Content>
						<AppLayout.Header>
							<Sidebar.Trigger />
						</AppLayout.Header>
						<AppLayout.Body asChild>
							<Main>
								<Outlet />
							</Main>
						</AppLayout.Body>
					</AppLayout.Content>
				</AppLayout.Workspace>
			</AppLayout.Root>
		</Sidebar.Root>
	);
}
```

`defaultOpen` is correct here — **not** controlled `open`. The value is already available at the server
render and the hydration render, so the uncontrolled state initializes to the right value once and stays
there; the server HTML ships `data-state="collapsed"` directly, with zero flash.

`extractSidebarStateCookie` returns `boolean | undefined` rather than `boolean` on purpose: a first-time
visitor with no cookie is not the same as someone who deliberately collapsed the rail, and folding the two
together would collapse the sidebar for everyone's first visit. Choose the default explicitly with `?? true`.

`serializeSidebarStateCookie` returns a plain cookie string, valid for both `document.cookie` on the client
and a `Set-Cookie` header on the server, so it works whichever side of your app owns the write. `Secure` is
omitted by default so the same call persists over `http://localhost` — if your policy requires it, pass
`{ secure: true }`. There is no `HttpOnly` option: the browser has to write this cookie when the user toggles
the rail.

## Accessibility

- `Sidebar.Nav` renders a `<nav>` landmark named `Main` by default; override `aria-label` when your app has
  multiple navigation landmarks (breadcrumbs, pagination) or for localization.
- `Sidebar.Trigger` follows the disclosure pattern: `aria-expanded` reflects the state and `aria-controls`
  references the nav. Keep a trigger visible at every breakpoint where the sidebar can collapse — a collapsed
  sidebar with no visible trigger is unrecoverable.
- `⌘B` / `Ctrl+B` toggles the sidebar. The modifier is resolved per platform — `⌘` on Apple platforms,
  `Ctrl` everywhere else — and the two never substitute for each other, so macOS's native `Ctrl+B`
  ("move the caret back one character", which every macOS text field binds) is left alone. The shortcut is
  also ignored while focus is in an `<input>`, `<textarea>`, `<select>`, or any `contenteditable` host,
  which covers embedded editors like Monaco and CodeMirror. Opt out entirely with
  `keyboardShortcut={false}` on `Sidebar.Root`.
- When the shell owns the document, pair the sidebar with a `SkipToMainLink` and compose `Main` onto
  `AppLayout.Body` so keyboard users can jump past the sidebar's tab gauntlet straight into the scrolling
  page region — see [App Layout → Landmarks](/layouts/app-layout#landmarks).
- The collapsed icon rail stays fully interactive: row labels are clipped and switcher text is visually
  hidden, but both remain in the tab order and the accessibility tree, so accessible names do not change
  between states.
- `Sidebar.ItemButton` `current` renders `aria-current="page"`, and the row's current treatment is styled from
  that attribute as well as `data-current` — so the announced state and the visual state cannot drift apart,
  whichever side sets it. `Sidebar.GroupLabel` is linked to its `Sidebar.List` via `aria-labelledby`.
- The mobile sheet is a modal dialog with focus trapping and `Escape` dismissal, courtesy of
  [Sheet](/components/overlays/sheet). Its accessible name follows the nav's (`"Main"` by default), so
  overriding `aria-label` or `aria-labelledby` on `Sidebar.Nav` renames the dialog too.
- The collapse/expand transitions respect `prefers-reduced-motion`.

### Sidebar.Root

The state owner. Renders no DOM.

| Prop                  | Type                      | Default | Description                                                                                                                                                                                                                          |
| --------------------- | ------------------------- | ------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| `defaultOpen?`        | `boolean`                 | `true`  | Initial desktop expanded state for the uncontrolled case.                                                                                                                                                                            |
| `open?`               | `boolean`                 | —       | Controlled desktop expanded state. Pair with `onOpenChange`.                                                                                                                                                                         |
| `onOpenChange?`       | `(open: boolean) => void` | —       | Called with the next desktop expanded state.                                                                                                                                                                                         |
| `openMobile?`         | `boolean`                 | —       | Controlled mobile sheet open state. Pair with `onOpenMobileChange`.                                                                                                                                                                  |
| `onOpenMobileChange?` | `(open: boolean) => void` | —       | Called with the next mobile sheet open state.                                                                                                                                                                                        |
| `mobileBreakpoint?`   | `"sm" \| "md" \| "lg"`    | `"lg"`  | Breakpoint below which `Sidebar.Nav` renders as a mobile `Sheet`.                                                                                                                                                                    |
| `keyboardShortcut?`   | `boolean`                 | `true`  | Toggle with `⌘B` (Apple) / `Ctrl+B` (elsewhere). Exact-modifier match, resolved per platform (`⌘⇧B` and macOS's native `Ctrl+B` pass through), and ignored while focus is in a text-editing or form control; set `false` to opt out. |

### Sidebar.Nav

The panel. All props from `div` plus the panel contract: `className`, `style`, `ref`, and rest props land on
the panel surface in both presentations (the desktop collapse container and the mobile `Sheet.Content`), and
`aria-label` (default `"Main"`) is forwarded to the inner `<nav>` landmark.

All props from [div](https://developer.mozilla.org/en-US/docs/Web/HTML/Element/div#attributes), plus:

| Prop               | Type     | Default  | Description                                                                                                                                                   |
| ------------------ | -------- | -------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `aria-label?`      | `string` | `"Main"` | Names the inner `<nav>` landmark, and the mobile `Sheet` dialog along with it. Override it for localization. Omitted when you pass `aria-labelledby` instead. |
| `aria-labelledby?` | `string` | —        | Names the `<nav>` from another element's id, and names the mobile sheet dialog directly. Takes precedence over the `aria-label` default.                      |
| `data-slot?`       | `string` | —        | An ancestor-forwarded `data-slot` chain, joined ahead of this part's own `sidebar-nav` rather than replacing it.                                              |

`Sidebar.Nav` takes no `asChild` — see [Polymorphism](#polymorphism).

| CSS Variable             | Default   | Description                                                                                                                                                                                                                                                                                   |
| ------------------------ | --------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `--sidebar-width`        | `16rem`   | Expanded desktop width (256px). Set it on `Sidebar.Nav` for one sidebar or on any ancestor (`:root`) for every sidebar — see [Width](#width).                                                                                                                                                 |
| `--sidebar-width-mobile` | `18rem`   | Mobile sheet width (288px). Set it on `Sidebar.Nav` or any ancestor — see [Width](#width).                                                                                                                                                                                                    |
| `--sidebar-width-icon`   | `3.25rem` | Collapsed icon rail width (52px). **Data attributes**

| Data Attribute  | Value                         | Description                                                                                                                                                                                                                                      |
| --------------- | ----------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| `data-state`    | `"expanded"` \| `"collapsed"` | On the desktop panel surface. Mirrors the root's expanded state and drives the width collapse to the icon rail; descendant parts style off it with `group-data-[state=collapsed]/sidebar-nav:`.                                                  |
| `data-hydrated` | present after hydration       | Presence-only, desktop panel surface. The CSS-side twin of the `isHydrated` gate: descendant collapse transitions are enabled only under `group-data-hydrated/sidebar-nav:`, so an SSR state correction snaps instead of animating on page load. |

| `data-state`    | `"open"` \| `"closed"`        | In the mobile sheet only, where the panel _is_ the `Sheet`'s Radix dialog content element and Radix owns the attribute — the sheet's open/close animation state, not the desktop expanded state. Consumers style against it too.                 |

### Sidebar.Trigger

An [IconButton](/components/actions/icon-button) wired to toggle the sidebar. All `IconButton` props except
`asChild` and `children`, with sidebar defaults:

| Prop          | Type                                | Default                 | Description                                                                                                                                                                                                                     |
| ------------- | ----------------------------------- | ----------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `appearance?` | `"ghost" \| "outlined"`             | `"ghost"`               | The visual style of the trigger.                                                                                                                                                                                                |
| `icon?`       | `ReactNode`                         | `<SidebarSimpleIcon />` | The icon rendered inside the trigger.                                                                                                                                                                                           |
| `intent?`     | `"accent" \| "danger" \| "neutral"` | `"neutral"`             | The color intent of the trigger.                                                                                                                                                                                                |
| `label?`      | `string`                            | `"Toggle Sidebar"`      | Accessible name, and what the tooltip says; override for localization.                                                                                                                                                          |
| `shortcut?`   | `ReactNode`                         | —                       | Chord chips rendered after the label in the tooltip — usually `<><MetaKey /><Kbd>B</Kbd></>`. Dropped under `Sidebar.Root keyboardShortcut={false}`, and `aria-hidden` because `aria-keyshortcuts` already announces the chord. |

The button is icon-only at every breakpoint, so it always renders a tooltip showing `label`. **That means it
requires a [`TooltipProvider`](/components/overlays/tooltip#tooltipprovider) ancestor, like any
`Tooltip.Root`, and throws without one** — mount a single provider at your app root, decoupled from the
sidebar, so the app-wide delay and hover settings stay app-wide. It also stamps `aria-keyshortcuts`
(`"Meta+B"` on Apple platforms, `"Control+B"` elsewhere, resolved after hydration), omitted along with the
chips under `Sidebar.Root keyboardShortcut={false}`.

**Data attributes**

| Data Attribute | Value                         | Description                                                                                                                                      |
| -------------- | ----------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------ |
| `data-state`   | `"expanded"` \| `"collapsed"` | Mirrors what the trigger toggles: the mobile sheet below the root's `mobileBreakpoint`, the desktop panel otherwise. Pairs with `aria-expanded`. |
| `data-slot`    | `"sidebar-trigger-tooltip"`   | On the tooltip surface, not the button — the styling hook for the label-and-chord popup this part renders.                                       |

### Sidebar.Header

The pinned structural container at the top of `Sidebar.Nav` — the app/product switcher row lives here. Its
**first child** owns a band exactly `--sidebar-header-height` tall (default `4.5rem`) and centers inside it.
When the sidebar composes into an `AppLayout`,
[`AppLayout.Header`](/layouts/app-layout#applayoutheader) derives its own height from the same token, so the
two rows stay center-aligned by construction.

Every child after the first stacks below the band in its own row, and the header grows to fit. That is how a
[search row](#the-search-row) pins under the switcher: the band — and with it the toolbar — stays the height
of the switcher row alone, and the row inherits the header's gutter, so neither the token nor the padding
needs a copy. The alignment is positional, so keep the aligned row as the header's first direct child. A
wrapper around both rows takes the band itself, and a first row taller than the band overflows it.

> [!NOTE]
> **The alignment is a desktop-only coupling.** `AppLayout.Header` finds the sidebar header with
> `:has()` from `AppLayout.Root`. Below `mobileBreakpoint` the sidebar renders inside a `Sheet` that portals
> to `document.body` — outside the shell subtree — so the selector stops matching and `AppLayout.Header`
> falls back to its standalone `h-14` (56px) from the derived 54px. That 2px change lands after hydration,
> because the server renders desktop-first. It is invisible in practice and there is nothing to align to on
> mobile (the sidebar header is inside a closed sheet), but if you are diffing layout snapshots across
> breakpoints, that is where the 2px comes from.

All props from [div](https://developer.mozilla.org/en-US/docs/Web/HTML/Element/div#attributes), plus:

| Prop       | Type      | Default | Description                                                                                                                 |
| ---------- | --------- | ------- | --------------------------------------------------------------------------------------------------------------------------- |
| `asChild?` | `boolean` | `false` | Use the `asChild` prop to compose the `Sidebar.Header` styling onto alternative element types or your own React components. |

| CSS Variable              | Default  | Description                                                                                                                                                                                                                                                                                                                                                      |
| ------------------------- | -------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `--sidebar-header-height` | `4.5rem` | The first child's band (72px) — the height [`AppLayout.Header`](/layouts/app-layout#applayoutheader) matches, not a cap on the header, which grows for every row after the first. Set it on a common ancestor of the sidebar and the app-layout header — e.g. `AppLayout.Root` — not on `Sidebar.Nav`, so both rows read the same value and stay center-aligned. |

### Sidebar.ItemButton

The interactive navigation row. Expanded spacing matches the regular sidebar; in the collapsed icon rail,
item rows keep their original square icon chip with a small offset so body and footer icons stay aligned
without text peeking from the rail.

The row sizes its **leading** icon (20px) and leaves trailing visuals — a menu caret, a count, a status
pip — to size themselves, so composing one needs no `!` override. A row composed with
`DropdownMenu.Trigger asChild` also stays highlighted while its menu is open (`data-state="open"`, supplied
by the trigger), and takes the same `--sidebar-row-width` floor on its menu as a switcher row (see
[Sizing a menu to a sidebar row](#sizing-a-menu-to-a-sidebar-row)). That is how the **Help** row is built in
the shell demo at the top of this page and in the live example under
[Labeling the rail for pointer users](#labeling-the-rail-for-pointer-users).

All props from `button` plus:

| Prop       | Type      | Default | Description                                                                                                                                     |
| ---------- | --------- | ------- | ----------------------------------------------------------------------------------------------------------------------------------------------- |
| `asChild?` | `boolean` | `false` | Render the single child (e.g. a router link) instead of a `<button>`.                                                                           |
| `current?` | `boolean` | —       | Marks the current page: sets `aria-current="page"` and `data-current`. Not needed for a child that marks itself, like react-router's `NavLink`. |

**Data attributes**

| Data Attribute | Value                   | Description                                                                                                                                                                   |
| -------------- | ----------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `data-slot`    | `"sidebar-item-button"` | Names the part, with any composing ancestor's chain ahead of it.                                                                                                              |
| `data-current` | present when `current`  | Presence-only — never `"false"`, since the `data-current:` variant matches the attribute's existence. Styles the current row.                                                 |
| `aria-current` | `"page"` when `current` | Set alongside `data-current`. The current-row styling follows _either_, so a composed child that marks itself (react-router's `NavLink`) gets the treatment without the prop. |
| `data-state`   | `"open"`                | **Read, not stamped** — supplied by a composing `DropdownMenu.Trigger` / `Dialog.Trigger`. The row styles against it so it stays highlighted while its menu is open.          |

### Sidebar.SearchTrigger

The row that opens a search or command palette. Place it in `Sidebar.Body` above the first `Sidebar.Group`, so
it shares the column the navigation rows use in both panel states and scrolls with them, or in
[`Sidebar.Header`](#sidebarheader) when it has to stay pinned while the navigation scrolls — see
[The search row](#the-search-row).

It is deliberately a navigation row and not a text field. The row is the same chrome as a
`Sidebar.ItemButton` — same height, padding, radius, hover, and the same 28px chip in the collapsed icon rail —
because a search entry point in a sidebar is one of the rows, not a form control wedged among them. Its
`shortcut` hint appears on hover or keyboard focus and is otherwise invisible, which keeps the resting panel
quiet.

A styled button only — compose it with
[`Command.SearchTrigger`](/components/navigation/command#commandsearchtrigger), which supplies the dialog
wiring, `aria-keyshortcuts`, and the behavior that makes typing or pasting into the row open the palette with
that text already in the query. Wrap the pair in `Sidebar.Tooltip` so the row keeps a visible label in the rail.

All props from [button](https://developer.mozilla.org/en-US/docs/Web/HTML/Element/button#attributes), plus:

| Prop        | Type        | Default | Description                                                                                                                                                                       |
| ----------- | ----------- | ------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `shortcut?` | `ReactNode` |         | The keyboard hint for the chord that opens the same palette, usually `<><MetaKey /><Kbd>K</Kbd></>`. Rendered pinned to the row's end, `aria-hidden`, revealed on hover or focus. |
| `asChild?`  | `boolean`   | `false` | Use the `asChild` prop to compose the `Sidebar.SearchTrigger` styling onto alternative element types or your own React components.                                                |

**Data attributes**

| Data Attribute | Value                      | Description                                                                                                                                        |
| -------------- | -------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------- |
| `data-slot`    | `"sidebar-search-trigger"` | Names the part, with any composing ancestor's chain ahead of it — `"command-search-trigger sidebar-search-trigger"` once a palette wraps it.       |
| `data-state`   | `"open"` \| `"closed"`     | **Read, not stamped** — supplied by the composing `Command.SearchTrigger` / `Dialog.Trigger`. The row stays highlighted while its palette is open. |

The `shortcut` hint is dropped outright in the collapsed rail — the chip has room for the icon and nothing
else, and `aria-keyshortcuts` already announces the chord. The row's label is clipped rather than removed, so
the button keeps its accessible name as a chip.

### Sidebar.SwitcherTrigger

The styled switcher row for the header (app switcher) and footer (account/user row). Its leading visual is
size-7 to match selected rail icons while the row keeps a compact 36px footprint —
[Avatar](/components/data-display/avatar) is that size by default, which is what an account or user row puts
there. The control uses a custom 10px radius on all corners so product and account switchers share the same
shape around their rounded tiles. A styled button only — compose it with `DropdownMenu.Trigger asChild` or
`Dialog.Trigger asChild`, which set the open state (`data-state="open"` styling responds automatically).

Match the trailing affordance to the surface the trigger actually opens. A `CaretDown` promises a menu
dropping from the row, so keep it for `DropdownMenu`-backed switchers; a `Dialog`-backed switcher reads
better with `CaretUpDown`, which says "pick one of several" without pointing anywhere.

All props from [button](https://developer.mozilla.org/en-US/docs/Web/HTML/Element/button#attributes), plus:

| Prop       | Type      | Default | Description                                                                                                                          |
| ---------- | --------- | ------- | ------------------------------------------------------------------------------------------------------------------------------------ |
| `asChild?` | `boolean` | `false` | Use the `asChild` prop to compose the `Sidebar.SwitcherTrigger` styling onto alternative element types or your own React components. |

**Data attributes**

| Data Attribute | Value                        | Description                                                                                                                                                            |
| -------------- | ---------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `data-slot`    | `"sidebar-switcher-trigger"` | Names the part, with any composing ancestor's chain ahead of it.                                                                                                       |
| `data-state`   | `"open"`                     | **Read, not stamped** — supplied by the composing `DropdownMenu.Trigger` / `Dialog.Trigger`. The row styles against it so it stays highlighted while its menu is open. |

Inside the collapsed icon rail, the row collapses to its **first child element** — the
leading visual — and the remaining children become visually hidden while staying in the accessibility tree,
so the button's accessible name is unchanged. Wrap loose text in an element (e.g. a `<span>`) so it
participates. Because the row shrinks, give the menu it opens the `--sidebar-row-width` floor
(`className="min-w-(--sidebar-row-width)"`) so the menu keeps the expanded row's width — see
[Sizing a menu to a sidebar row](#sizing-a-menu-to-a-sidebar-row).

### Sidebar.Tooltip

Labels a row while — and only while — the desktop panel is collapsed to the icon rail. See
[Labeling the rail for pointer users](#labeling-the-rail-for-pointer-users). Requires a
[`TooltipProvider`](/components/overlays/tooltip#tooltipprovider) ancestor and must be inside a
`Sidebar.Root` (it throws otherwise).

It opens on hover or focus like any tooltip and closes when the pointer leaves the row — the label itself is
not hoverable. The rail state vetoes it: the expanded panel and the mobile sheet never show it, and toggling
the rail dismisses whatever was showing, so collapsing the panel cannot pop a label under a pointer that has
already moved on.

Its props are [`Tooltip.Content`](/components/overlays/tooltip#tooltipcontent)'s, minus the two this row
owns, plus:

| Prop         | Type                                           | Default   | Description                                                                                                                                                                                                                                                                 |
| ------------ | ---------------------------------------------- | --------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `children`   | `ReactElement`                                 | —         | The single element row to label: a `Sidebar.ItemButton` or `Sidebar.SwitcherTrigger`, optionally already wrapped in a `DropdownMenu.Trigger asChild`. Required — `Tooltip.Trigger asChild` clones it, so text or no child renders nothing hoverable and is a compile error. |
| `label`      | `ReactNode`                                    | —         | What the tooltip says — normally the row's own label text.                                                                                                                                                                                                                  |
| `shortcut?`  | `ReactNode`                                    | —         | Chord chips rendered after the label — usually `<><MetaKey /><Kbd>K</Kbd></>`. The rail hides the row's own hint along with its text, so the tooltip is where a pointer user can still learn it. `aria-hidden`, since the row's `aria-keyshortcuts` already announces it.   |
| `side?`      | `"top"` \| `"right"` \| `"bottom"` \| `"left"` | `"right"` | Which side of the row the tooltip opens on. The rail sits at the inline start of the viewport, so the default points the tooltip away from it.                                                                                                                              |
| `asChild?`   | `boolean`                                      | `false`   | Radix's own `Tooltip.Content` swap, forwarded straight through: it replaces the **tooltip surface**, not the row you wrap — see [Polymorphism](#polymorphism).                                                                                                              |
| `className?` | `string`                                       | —         | Merged onto the tooltip surface, last, by `Tooltip.Content` — this part adds no classes of its own.                                                                                                                                                                         |
| `data-slot?` | `string`                                       | —         | An ancestor-forwarded `data-slot` chain, joined ahead of this part's own `sidebar-tooltip` rather than replacing it.                                                                                                                                                        |

Every remaining `Tooltip.Content` prop — `style`, `ref`, `align`, `sideOffset`, `collisionPadding`, any
`data-*` — lands on the tooltip surface as usual, and so do the attributes
[Tooltip](/components/overlays/tooltip#tooltipcontent) itself emits there (`data-state`, `data-side`). The
four in the table above are the exceptions: this part reads them itself.

**Data attributes**

| Data Attribute | Value               | Description                                                                                    |
| -------------- | ------------------- | ---------------------------------------------------------------------------------------------- |
| `data-slot`    | `"sidebar-tooltip"` | On the tooltip surface, with any forwarded chain ahead of it. Styling and test-targeting hook. |

### serializeSidebarStateCookie

Serializes the expanded state as a cookie string, valid for both `document.cookie` and a `Set-Cookie` header.
No `HttpOnly` option: the browser writes this cookie from `onOpenChange`.

| Param       | Type                                 | Default | Description                                                                   |
| ----------- | ------------------------------------ | ------- | ----------------------------------------------------------------------------- |
| `open`      | `boolean`                            | —       | Whether the sidebar is expanded.                                              |
| `options?`  | `SerializeSidebarStateCookieOptions` | `{}`    | Cookie attributes; see below.                                                 |
| **returns** | `string`                             | —       | e.g. `mantle-sidebar-state=collapsed; Max-Age=31536000; Path=/; SameSite=Lax` |

| Option      | Type                          | Default    | Description                                                                            |
| ----------- | ----------------------------- | ---------- | -------------------------------------------------------------------------------------- |
| `maxAge?`   | `number`                      | `31536000` | Lifetime in seconds (one year).                                                        |
| `path?`     | `string`                      | `"/"`      | Path the cookie applies to.                                                            |
| `domain?`   | `string`                      | —          | Omitted by default (exact host). Set e.g. `".example.com"` to share across subdomains. |
| `sameSite?` | `"Lax" \| "Strict" \| "None"` | `"Lax"`    | `SameSite` policy.                                                                     |
| `secure?`   | `boolean`                     | `false`    | Omitted by default so the cookie is not rejected over `http://localhost`.              |
