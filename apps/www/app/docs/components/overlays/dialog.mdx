# Dialog

A window overlaid on either the primary window or another dialog window, rendering the content underneath inert.

<Example name="components/overlays/dialog/overview" title="Dialog example">

```tsx
import { Dialog } from "@ngrok/mantle/dialog";
import { Button } from "@ngrok/mantle/button";

<Dialog.Root>
	<Dialog.Trigger asChild>
		<Button type="button" appearance="filled" intent="neutral">
			Open dialog
		</Button>
	</Dialog.Trigger>
	<Dialog.Content>
		<Dialog.Header>
			<Dialog.Title>Are you absolutely sure?</Dialog.Title>
			<Dialog.CloseIconButton />
		</Dialog.Header>
		<Dialog.Body>
			This action cannot be undone. This will permanently delete your account and remove your data
			from our servers.
		</Dialog.Body>
		<Dialog.Footer>
			<Dialog.Close asChild>
				<Button type="button" intent="neutral" appearance="outlined">
					Cancel
				</Button>
			</Dialog.Close>
			<Dialog.Close asChild>
				<Button type="button" intent="danger" appearance="filled">
					Delete
				</Button>
			</Dialog.Close>
		</Dialog.Footer>
	</Dialog.Content>
</Dialog.Root>;
```

## When to use

- Interrupt the user in a centered modal to gather input or confirm a choice that is not destructive.
- Prefer [`AlertDialog`](/components/overlays/alert-dialog) for a destructive or irreversible confirmation, such as a delete.
- Prefer [`Sheet`](/components/overlays/sheet) for side-panel content, such as a filter panel, a detail view, or a navigation drawer.
- Prefer [`Popover`](/components/overlays/popover) for small content that opens next to its trigger, with no modal backdrop.

## Layering and z-index

`Dialog.Content` renders the browser's modal `<dialog>` (`data-slot="dialog-positioner"`), so it paints in the top layer, above the page and every float outside it. The browser makes the page behind it inert, closes it on Escape, and returns focus to the trigger. Floats composed inside the content portal into the `<dialog>` and paint above the content. A dialog that opens from inside another one paints above it.

`Dialog`, `Sheet`, and `AlertDialog` each draw their own backdrop, so stacking modal layers compounds the dim and blur effect on the layers underneath.

## Tab at the end of a dialog

Tab from the last control in an open modal dialog moves focus to the browser UI, such as the address bar. More Tab presses bring focus back into the dialog. Shift+Tab from the first control does the same in reverse. The page behind the dialog never takes focus. This is what Tab does at the end of any page. It differs from mantle 0.94.1 on purpose: that dialog wrapped Tab from the last control to the first.

mantle keeps the browser behavior because the HTML standard defines it and W3C's Accessible Platform Architectures (APA) Working Group endorsed it:

- **The HTML standard.** [`showModal()`](https://html.spec.whatwg.org/multipage/interactive-elements.html#show-a-modal-dialog) sets the document to be [blocked by the modal dialog](https://html.spec.whatwg.org/multipage/interaction.html#blocked-by-a-modal-dialog). While it is blocked, every node outside the dialog "must become inert". [Sequential focus navigation](https://html.spec.whatwg.org/multipage/interaction.html#sequential-focus-navigation) has no exception for dialogs. When the document has no next control, "the user agent should transfer focus to its own controls appropriately (if any)". Chrome, Firefox, and Safari all move focus out of the page in this case.
- **The discussion.** [whatwg/html#8339](https://github.com/whatwg/html/issues/8339) asked for a focus trap in `showModal()` in 2022. An HTML editor, quoted in the issue, wrote that the spec "indicates that browsers' current behavior is correct". In November 2023, the APA Working Group concluded that "the current behavior of the native dialog element should be kept as it is". It gave two reasons: keyboard users can "open a new tab to look something important up or to change a browser setting", and the browser UI is "an additional natural escape mechanism" in kiosk situations. The requester then closed the issue.
- **WCAG.** In August 2025, [w3c/wcag#4381](https://github.com/w3c/wcag/pull/4381) changed the modal dialog example in [Understanding 2.4.3 Focus Order](https://www.w3.org/WAI/WCAG22/Understanding/focus-order.html). It now says that content outside the dialog "becomes inert and cannot receive focus (though, depending on implementation, the focus cycle might still include user agent controls)". [Understanding 2.1.2 No Keyboard Trap](https://www.w3.org/WAI/WCAG22/Understanding/no-keyboard-trap.html) still describes a wrap, with the same note that "the focus cycle might still include user agent controls".
- **Why the APG says to wrap.** The [APG Dialog (Modal) Pattern](https://www.w3.org/WAI/ARIA/apg/patterns/dialog-modal/) still tells Tab to move from the last tabbable element to the first. In #8339, Scott O'Hara explained that this guidance and the old WCAG example "were written long before the `inert` attribute or the `<dialog>` element were widely supported". A custom dialog without `inert` had to take every page control out of the tab order, so a trap was "far easier". The APG is not normative. [w3c/aria-practices#1772](https://github.com/w3c/aria-practices/issues/1772) asks the APG to allow Tab to reach the browser UI. The APG Task Force discussed it in August 2025 and kept the wrap.

Do not add a focus trap on top of the dialog. The page behind stays out of reach, and keyboard users keep the same way out of the page that they have everywhere else.

## UI above an open dialog

An open dialog makes the rest of the page inert: no click, focus, or screen reader reaches it. To keep a banner or a bar usable above it, wrap the element in [`OverlayPrompt`](/components/primitives/overlay-prompt): it moves into the open dialog, so it paints above it, takes clicks and focus, and a press in it does not close the dialog. mantle's `Toaster` and `Sandbar` use it.

## Third-party popups

A script can show its own popup in a frame on `<body>`. A payment script does this for a 3-D Secure challenge and for a wallet sign-in, and a captcha does it for a challenge. A modal dialog makes that frame inert and paints over it. Set `modal={false}` on a dialog that holds such a flow:

```tsx
<Dialog.Root modal={false}>
```

A dialog that is not modal has no backdrop, paints at Tailwind `z-60`, and leaves the page live. Escape and a press outside close it. While a frame is on top at the center of the viewport, the dialog yields to the popup:

- Escape does not close the dialog. It moves focus into the popup, and the popup then takes the keyboard.
- A press in the popup is not a press outside.

Close the dialog from your code only after the popup closes. [Third-party popups](/components/overlays/sheet#third-party-popups) on the Sheet page has the reason, the rule for what counts as a popup, and an example.

## Handling autofill overlays

When a dialog contains form inputs, browser autofill or password-manager plugins (e.g. 1Password) may render overlays as siblings to the dialog content. A click on such an overlay can trigger `onPointerDownOutside`, which closes the dialog. A press on the backdrop targets the `<dialog>`, which `isDialogOverlayTarget` names. Use it to close the dialog on the backdrop only:

```tsx
import { Dialog, isDialogOverlayTarget } from "@ngrok/mantle/dialog";

<Dialog.Content
	onPointerDownOutside={(event) => {
		// Allow closing only when clicking the actual overlay backdrop,
		// not browser autofill/password-manager popups
		if (isDialogOverlayTarget(event.target)) {
			return;
		}
		event.preventDefault();
	}}
>
	{/* dialog content with form inputs */}
</Dialog.Content>;
```

Compose the parts of a `Dialog` together to build your own:

```text showLineNumbers=false

├── Dialog.Trigger
└── Dialog.Content
    ├── Dialog.Header
    │   ├── Dialog.Title
    │   ├── Dialog.Description
    │   └── Dialog.CloseIconButton
    ├── Dialog.Body
    └── Dialog.Footer
        └── Dialog.Close
```

## Full-page dialog

Every dialog already sits 16px from each viewport edge: `Dialog.Content` positions itself inside a `fixed inset-4` wrapper, so you never add that margin yourself. `appearance` decides how much of the box it claims from there:

| `appearance`   | Width                      | Viewport inset | Corners and border   |
| -------------- | -------------------------- | -------------- | -------------------- |
| `"centered"`   | capped at `preferredWidth` | 16px           | rounded and bordered |
| `"full-page"`  | fills the box              | 16px           | rounded and bordered |
| `"full-bleed"` | fills the box              | none           | square, no border    |

The three values move together as one decision, because a dialog that fills the viewport has no width left to cap and no corner left to round. `preferredWidth` therefore belongs to `"centered"` only: passing it beside `"full-page"` or `"full-bleed"` is a type error, not a prop that silently does nothing.

```tsx
// a card, capped (the default)
<Dialog.Content preferredWidth="max-w-2xl">

// fills the 16px-inset box, still a rounded card
<Dialog.Content appearance="full-page">

// fills the whole viewport, square and unbordered
<Dialog.Content appearance="full-bleed">
```

The parts keep their roles at every appearance. Because `Dialog.Content` is a flex column with `Dialog.Body` at `flex-1 overflow-y-auto`, the header and footer stay pinned while the body scrolls.

When the content needs the whole viewport, reach for this: a request log, a diff, a media preview, a multi-column editor. When the content deserves its own URL, a back button, or a shareable link, a route beats a dialog.

`"full-bleed"` keeps its backdrop. The content opens at `zoom-in-95`, so a sliver of viewport edge stays uncovered for the length of the animation, and the backdrop is what fills it.

The switch in the demo body swaps `"full-page"` for `"full-bleed"`.

<Example name="components/overlays/dialog/full-page-dialog" title="Dialog full-page dialog example">

							</div>

				</Dialog.Body>
				<Dialog.Footer>

## Stacking a Sheet over a Dialog

A modal `Dialog` and `Sheet` each open in the top layer, so the one that opened last paints on top. Open the dialog below first, then open the sheet from inside it: the sheet stacks over the dialog rather than disappearing behind it. Each overlay draws its own backdrop, so the sheet's backdrop dims the dialog beneath.

## With TanStack Form

Use [TanStack Form](https://tanstack.com/form) with [`Field`](/components/forms/field) to gather validated input in a dialog. `Dialog.Content` is a flex column, so wrap `Dialog.Body` and `Dialog.Footer` in a `display: contents` form: the footer's submit button participates in the form while the body keeps its scrollable layout. Close the dialog from the form's `onSubmit` (it only runs once validation passes) and reset the form when the dialog closes so a cancelled draft doesn't leak into the next open. The form sets `noValidate` so the browser's native `type="email"` validation doesn't block the submit event: the schema owns validation and errors render consistently through `Field.Errors`.

If password managers or browser autofill overlays interfere with outside-click dismissal, see [Handling autofill overlays](#handling-autofill-overlays).

<Example name="components/overlays/dialog/with-tanstack-form" title="Dialog With TanStack Form example">

```tsx
import { Button } from "@ngrok/mantle/button";
import { Dialog } from "@ngrok/mantle/dialog";
import { Field, toErrorMessages } from "@ngrok/mantle/field";
import { Input } from "@ngrok/mantle/input";
import { Select } from "@ngrok/mantle/select";
import { useForm } from "@tanstack/react-form";
import { useRef, useState } from "react";
import { z } from "zod";

const formSchema = z.object({
	email: z.email("Enter a valid email address."),
	role: z.string().min(1, "Choose a role."),
});

function Example() {
	const [open, setOpen] = useState(false);
	const formRef = useRef<HTMLFormElement>(null);
	const form = useForm({
		defaultValues: {
			email: "",
			role: "",
		},
		validators: {
			onSubmit: formSchema,
		},
		// Why: a failed submit moves focus to the first invalid field, so a screen
		// reader says what to fix. The frame lets the fields render their errors first.
		onSubmitInvalid: () => {
			requestAnimationFrame(() => {
				formRef.current?.querySelector<HTMLElement>('[aria-invalid="true"]')?.focus();
			});
		},
		onSubmit: ({ value }) => {
			// Handle the invite with `value`, then close the dialog
			handleOpenChange(false);
		},
	});

	const handleOpenChange = (nextOpen: boolean) => {
		setOpen(nextOpen);
		if (!nextOpen) {
			form.reset();
		}
	};

	return (
		<Dialog.Root open={open} onOpenChange={handleOpenChange}>
			<Dialog.Trigger asChild>
				<Button type="button" appearance="filled" intent="neutral">
					Invite a teammate
				</Button>
			</Dialog.Trigger>
			<Dialog.Content>
				<Dialog.Header>
					<Dialog.Title>Invite a teammate</Dialog.Title>
					<Dialog.CloseIconButton />
				</Dialog.Header>
				<form
					ref={formRef}
					className="contents"
					noValidate
					onSubmit={(event) => {
						event.preventDefault();
						event.stopPropagation();
						void form.handleSubmit();
					}}
				>
					<Dialog.Body className="space-y-4">
						<form.Field name="email">
							{(field) => (
								<Field.Item name={field.name}>
									<Field.Label>Email</Field.Label>
									<Field.Control>
										<Input
											type="email"
											placeholder="teammate@example.com"
											value={field.state.value}
											onBlur={field.handleBlur}
											onChange={(event) => field.handleChange(event.target.value)}
										/>
									</Field.Control>
									<Field.Errors messages={toErrorMessages(field.state.meta.errors)} />
								</Field.Item>
							)}
						</form.Field>
						<form.Field name="role">
							{(field) => (
								<Field.Item name={field.name}>
									<Field.Label>Role</Field.Label>
									<Field.Control>
										<Select.Root
											value={field.state.value}
											onBlur={field.handleBlur}
											onValueChange={field.handleChange}
										>
											<Select.Trigger>
												<Select.Value placeholder="Select a role" />
											</Select.Trigger>
											<Select.Content width="trigger">
												<Select.Item value="admin">Admin</Select.Item>
												<Select.Item value="developer">Developer</Select.Item>
												<Select.Item value="read-only">Read-only</Select.Item>
											</Select.Content>
										</Select.Root>
									</Field.Control>
									<Field.Errors messages={toErrorMessages(field.state.meta.errors)} />
								</Field.Item>
							)}
						</form.Field>
					</Dialog.Body>
					<Dialog.Footer>
						<Dialog.Close asChild>
							<Button type="button" appearance="outlined" intent="neutral">
								Cancel
							</Button>
						</Dialog.Close>
						<Button type="submit" appearance="filled" intent="neutral">
							Send invite
						</Button>
					</Dialog.Footer>
				</form>
			</Dialog.Content>
		</Dialog.Root>
	);
}
```

## Polymorphism

`Dialog.Trigger`, `Dialog.Close`, `Dialog.Title`, `Dialog.Description`, and `Dialog.CloseIconButton` accept `asChild`, which renders your single child in place of the part's default element while keeping its styling and behavior.

`Dialog.Trigger asChild` is by far the most common: it makes your own `Button` open the dialog instead of nesting a button inside one. Use `Dialog.Close asChild` to let any element dismiss the dialog, and `Dialog.Title asChild` when the heading level must fit the surrounding page outline.

`Dialog.Root` renders no DOM of its own, so it takes no `asChild`. `Dialog.Content` renders a `<dialog>` and its panel, and `Dialog.Header`, `Dialog.Body`, and `Dialog.Footer` are plain layout `<div>`s. None of them accepts it.

## Keep the dialog mounted

By default, `Dialog.Content` mounts when the dialog opens and unmounts after its exit animation. With `forceMount`, the content stays mounted and the server renders it, closed. An uncontrolled `Dialog.Trigger` then opens it with a DOM call and no React render, even before the page hydrates. Use it for a dialog that a tap must open in the next frame on a slow phone, such as a menu. It costs the HTML and the hydration of the content on each page load.

```tsx
<Dialog.Content forceMount>
```

## API Reference

The `Dialog` components are built on the browser's [`<dialog>` element](https://developer.mozilla.org/en-US/docs/Web/HTML/Reference/Elements/dialog).

### Dialog.Root

The root stateful component that manages the open/closed state of the dialog.

| Prop            | Type                      | Default | Description                                                                                                                                                                                    |
| --------------- | ------------------------- | ------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `open?`         | `boolean`                 |         | The controlled open state of the dialog. Must be used in conjunction with `onOpenChange`.                                                                                                      |
| `onOpenChange?` | `(open: boolean) => void` |         | Event handler called when the open state of the dialog changes.                                                                                                                                |
| `defaultOpen?`  | `boolean`                 | `false` | The open state of the dialog when it is initially rendered. Use when you do not need to control its open state.                                                                                |
| `modal?`        | `boolean`                 | `true`  | Whether the page behind the dialog is inert. Set `false` for a dialog that holds a third-party frame, such as a payment challenge or a captcha. See [Third-party popups](#third-party-popups). |

### Dialog.Trigger

A button that opens the dialog.

| Prop       | Type      | Default | Description                                                                          |
| ---------- | --------- | ------- | ------------------------------------------------------------------------------------ |
| `asChild?` | `boolean` | `false` | Use the `asChild` prop to compose the trigger functionality onto your own component. |

### Dialog.Content

The panel of the dialog, centered in the viewport. `ref`, `className`, and other props target the panel.

`Dialog.Content` renders the panel inside a `<dialog>` (`data-slot="dialog-positioner"`) that lays out the panel, draws the backdrop, and receives floats portaled from inside the dialog. The full stacking contract lives at [Stacking Layers](/base/stacking-layers).

| Prop                    | Type                                            | Default      | Description                                                                                                                                                                                                                     |
| ----------------------- | ----------------------------------------------- | ------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `appearance?`           | `"centered"` \| `"full-page"` \| `"full-bleed"` | `"centered"` | How much of the viewport the dialog claims. See [Full-page dialog](#full-page-dialog).                                                                                                                                          |
| `preferredWidth?`       | `` `max-w-${string}` ``                         | `"max-w-lg"` | The maximum width of a `"centered"` dialog, as a Tailwind `max-w-` class. Accepted for `appearance="centered"` only; a filled dialog has no width to cap.                                                                       |
| `forceMount?`           | `true`                                          |              | Keeps the content mounted while the dialog is closed, so the server renders it and a tap opens it with no React render. See [Keep the dialog mounted](#keep-the-dialog-mounted).                                                |
| `onOpenAutoFocus?`      | `(event: Event) => void`                        |              | Event handler called after the dialog opens and the browser moves focus into it. Call `event.preventDefault()` and focus an element of your choice.                                                                             |
| `onCloseAutoFocus?`     | `(event: Event) => void`                        |              | Event handler called after the dialog closes and the browser returns focus to the trigger.                                                                                                                                      |
| `onEscapeKeyDown?`      | `(event: KeyboardEvent) => void`                |              | Event handler called when the escape key is down. It can be prevented by calling `event.preventDefault`.                                                                                                                        |
| `onInteractOutside?`    | `(event: PointerDownOutsideEvent) => void`      |              | Event handler called on the same presses as `onPointerDownOutside`, after it. It can be prevented by calling `event.preventDefault`.                                                                                            |
| `onPointerDownOutside?` | `(event: PointerDownOutsideEvent) => void`      |              | Event handler called when a press starts on the backdrop, or anywhere outside a dialog that is not modal. It can be prevented by calling `event.preventDefault`. See [Handling autofill overlays](#handling-autofill-overlays). |

| Data Attribute    | Value                                           | Description                                                    |
| ----------------- | ----------------------------------------------- | -------------------------------------------------------------- |
| `data-appearance` | `"centered"` \| `"full-page"` \| `"full-bleed"` | Reflects the resolved `appearance`.                            |
| `data-open`       | present while open                              | Presence-only. The `[open]` mirror the open animation keys on. |
| `data-closing`    | present while the exit plays                    | Presence-only. Drives the close animation.                     |

### Dialog.Header

Contains the title, the description, and the close button of the dialog. `Dialog.Title` and `Dialog.Description` stack in a column. Every other child shares the title's row, so a long title truncates beside `Dialog.CloseIconButton`. See [Header with a description](#header-with-a-description).

| Prop       | Type        | Default | Description                                     |
| ---------- | ----------- | ------- | ----------------------------------------------- |
| `children` | `ReactNode` |         | The content to render inside the dialog header. |

### Dialog.Body

Contains the main content of the dialog.

| Prop       | Type        | Default | Description                                   |
| ---------- | ----------- | ------- | --------------------------------------------- |
| `children` | `ReactNode` |         | The content to render inside the dialog body. |

### Dialog.Footer

Contains the footer content of the dialog, including action buttons.

| Prop       | Type        | Default | Description                                                                        |
| ---------- | ----------- | ------- | ---------------------------------------------------------------------------------- |
| `children` | `ReactNode` |         | The content to render inside the dialog footer. Typically contains action buttons. |

### Dialog.Title

An accessible name to be announced when the dialog is opened.

| Prop       | Type        | Default | Description                                                                       |
| ---------- | ----------- | ------- | --------------------------------------------------------------------------------- |
| `children` | `ReactNode` |         | The title text for the dialog.                                                    |
| `asChild?` | `boolean`   | `false` | Use the `asChild` prop to render a custom element instead of the default heading. |

### Dialog.Description

An accessible description to be announced when the dialog is opened.

| Prop       | Type        | Default | Description                                                                     |
| ---------- | ----------- | ------- | ------------------------------------------------------------------------------- |
| `children` | `ReactNode` |         | The description text for the dialog. It adds context for assistive technology.  |
| `asChild?` | `boolean`   | `false` | Use the `asChild` prop to render a custom element instead of the default `div`. |

### Dialog.Close

A button that closes the dialog when clicked.

| Prop       | Type      | Default | Description                                                                        |
| ---------- | --------- | ------- | ---------------------------------------------------------------------------------- |
| `asChild?` | `boolean` | `false` | Use the `asChild` prop to compose the close functionality onto your own component. |

### Dialog.CloseIconButton

An icon button that closes the dialog when clicked.

| Prop          | Type                                           | Default          | Description                                                                  |
| ------------- | ---------------------------------------------- | ---------------- | ---------------------------------------------------------------------------- |
| `size?`       | `"xs"` \| `"sm"` \| `"md"` \| `"lg"` \| `"xl"` | `"md"`           | The size of the close icon button.                                           |
| `label?`      | `string`                                       | `"Close Dialog"` | The accessible label for the close button. Important for screen readers.     |
| `appearance?` | `"filled"` \| `"ghost"` \| `"outlined"`        | `"ghost"`        | The visual appearance of the close icon button.                              |
| `intent?`     | `"neutral"`                                    | `"neutral"`      | The tone of the close icon button. `IconButton` draws the neutral tone only. |
