export function RegroupBarChartExample() {
	const [grouping, setGrouping] = useState("provider");
	const active = groupings[grouping];
	return (
		<div className="w-full">
			<div className="mb-3 flex flex-wrap gap-2">
				{Object.entries(groupings).map(([key, option]) => (
					<Button
						key={key}
						appearance={key === grouping ? "filled" : "outlined"}
						onClick={() => setGrouping(key)}
					>
						{option.label}
					</Button>
				))}
			</div>
			{/* No `key` on the Root: remounting it would replay the enter animation
			    on every switch and hide the behavior this example exists to show. */}
			<BarChart.Root data={active.data} xKey="month" aria-label="Monthly requests by grouping">
				<BarChart.Grid />
				<BarChart.XAxis tickFormat={(month) => String(month).slice(0, 3)} />
				<BarChart.YAxis />
				{active.series.map(([dataKey, label, color]) => (
					<BarChart.Bar key={dataKey} dataKey={dataKey} label={label} color={color} />
				))}
				<BarChart.Legend />
			</BarChart.Root>
		</div>
	);
}

# Bar Chart

A bar chart for comparing values across categories, with grouped and stacked variants.

## When to use

Use a `BarChart` to compare values across discrete categories: months, endpoints, plans. Bars encode value by length from a shared zero baseline, so the y-axis minimum is fixed at `0` and a truncated-bar axis is unrepresentable.

- Time-binned aggregates (requests per day, cost per week) are categories too: each bar is a bucket's total, so a dense daily chart like the one below belongs here.
- Grouped bars (the default) compare series side by side within each category.
- Stacked bars (`stacked` on the Root) show how parts compose each category's total.
- Prefer `LineChart` for trends over continuous time: sampled measurements at every timestamp read as a stream, not buckets.
- Prefer `AreaChart` for cumulative composition over continuous time.

**Keep a chart to eight series.** A legend of a dozen access keys is a list no reader can match to the bars, and every added color sits closer to one already on the chart. Rank the series by the window's total, keep the top seven, and sum the rest into one `"Other"` series. Series that belong to one thing are the exception: they can share one `color` and stay apart by `texture`. See [Sharing one color](#sharing-one-color) and [Color and accessibility](#color-and-accessibility).

```tsx
const TOP_N = 7;

/** The top-N keys by window total, with every other key summed into "Other". */
function foldTail(rows, keys) {
	const totals = keys.map((key) => ({
		key,
		total: rows.reduce((sum, row) => sum + (row[key] ?? 0), 0),
	}));
	const top = totals
		.toSorted((a, b) => b.total - a.total)
		.slice(0, TOP_N)
		.map(({ key }) => key);
	const tail = keys.filter((key) => !top.includes(key));
	const folded = rows.map((row) => ({
		...row,
		other: tail.reduce((sum, key) => sum + (row[key] ?? 0), 0),
	}));
	return { rows: folded, series: tail.length === 0 ? top : [...top, "other"] };
}
```

Give the fold's own series `color="neutral"`, so it reads as the tail and not as one more series. Other is always neutral. Keep it last, so it sits at the far end of a stack.

Compose everything inside `BarChart.Root`: gridlines, axes, one `BarChart.Bar` per series, and (on multi-series charts) the legend. The interaction layer (per-category hover band and tooltip, keyboard stepping, polite announcements, and an sr-only description) ships with `Root` unconditionally; the sr-only data table mounts once the chart takes focus.

Density takes care of itself: this chart plots 91 daily bars, and the band axis thins its own labels (evenly spaced from the first day, skipped rather than rotated when they'd collide). `Date` x values format as dates in the tooltip, land as exact ISO timestamps in the data-table twin, and take a `tickFormat` for short axis labels.

## Stacked bars

Add `stacked` to the Root to stack the composed series instead of grouping them. Bars stack from the baseline up in registration order: series that mount together register in composition order, so the first `BarChart.Bar` sits on the baseline and the last on top. A `Bar` that mounts later stacks on top of every series already registered, whatever its position in the JSX, and a `dataKey` that unmounts and returns resumes its original position. Reordering the parts of a mounted chart does not restack it: the position sticks to the `dataKey`, which is what keeps a series from jumping when you rename its `label`. The tooltip leads with the column's total, then lists the far end of the stack first, so a vertical chart reads top-down and a horizontal one reads from the far end back to the baseline.

gap is carved only where a neighbor adjoins. March carries one series, so its one segment wears both rounded

## Brand colors

A chart of named things (AI model providers, cloud vendors, plan tiers) often wants each thing's own brand color,
the same on every chart and every page. When no mantle color name fits, declare the values as custom properties
on the Root and pass each one to the matching series as a CSS string. The chart resolves them inside the Root's
own cascade. The legend swatch and the tooltip stroke emit the same `var()`, so one declaration set covers all
three surfaces.

Use `var(--your-token)` rather than a raw hex. A hex freezes: the same value paints on white and on near-black.
The dark theme cannot adjust it. A custom property lets you give each theme its own value, and the chart picks up
the new value whenever the theme changes.

A brand color is outside mantle's measured tokens, so check it against the card in both themes and against the
other colors on the chart. Series order decides whether a close pair bites, because a stacked chart only puts
consecutive series against each other. The example runs OpenAI, Claude, Gemini: under simulated color vision
deficiency (CVD), Claude's orange sits close to OpenAI's green, so Claude wears a `texture`. When a pair does
collide, reorder the series, change the color, or add a `texture`.

Brand colors have three more limits:

- Grouped bars compare every series to every other, not only its neighbors.
- Brand colors collide with each other. Five of the major AI providers use nearly the same blue.
- A black or near-black brand color carries no hue, so it reads as the neutral Other series.

## Horizontal bars

`orientation` names the direction the bars point, not an axis: `"vertical"` (the default) bars stand up, `"horizontal"` bars lie across. Set `orientation="horizontal"` to grow bars rightward from a left baseline with categories banded down the y axis. Reach for it when category labels are long (they read straight instead of angled or truncated under the axis) or when there are many categories to rank. `xKey` still names the category and `YAxis` still labels the value. Only the drawing flips: the category axis moves to the left gutter, the value axis to the bottom, and the baseline, reference lines, and the two rung textures (`"perpendicular"` and `"parallel"`) all rotate to match. The `"grid"` lattice inks both rung directions, so it looks the same either way. Everything else (grouping, stacking, hover, the data table) works unchanged. The keyboard follows the layout: the Down and Up arrow keys step through the categories, and Page Down and Page Up jump forward and back. The Left and Right arrow keys still work.

## Textures

When a multi-series or stacked chart can't rely on color alone (color-vision deficiencies, grayscale print and exports, forced-colors mode), give each series a fill `texture`. Textures are a redundant identity encoding alongside color: `"hatch"` (diagonal lines at 45°), `"hatch-reverse"` (its 135° mirror), `"crosshatch"` (both), `"perpendicular"` (rungs across the bar's length: horizontal lines on vertical bars), `"parallel"` (rungs along it: vertical lines on vertical bars), `"grid"` (both rung directions crossed), and `"dots"` (an offset dot field). The two rung textures flip with `orientation`, in opposite senses. Every other value draws the same whichever way the bars point, `"grid"` included: it is the orthogonal lattice against `"crosshatch"`'s diagonal one.

A textured series paints a light tint of its color (25% of the color mixed into the card surface) and draws the pattern's marks in the full color. A solid series and a textured series of one color therefore read as a pair: the dark member and the light member. Every legend key wears its series' pattern, so the mapping never depends on hue.

Texture is opt-in and purposeful, never decorative. Mantle assigns none of it for you. A bar carries no point [`shape`](/components/charts/scatter-plot#point-shapes), so the `texture` you set is a bar's only second channel. Keep solid fills when color alone already carries identity. When it does not, either leave the first series solid and texture the rest, or texture only the series in the pair that collides. The [Diverging stacks](#diverging-stacks) and [Brand colors](#brand-colors) examples above take the targeted form.

### Sharing one color

Several series can share one `color` and stay apart by `texture`. Reach for it when the series belong to one thing: zones of a region, shards of a cluster, tiers of one plan, or the In and Out traffic of one agent. The shared color reads as the family. Series that share no family belong in one `"Other"` series instead.

Two rules make it work:

- **Every member sets the same `color`.** The color names the family, not the member.
- **Every member carries its own `texture`.** Two series that share a color and a texture paint identically. Nothing warns you. One member may stay solid; the rest take a value each.

Count the costs before you reach for it. One hue no longer names one series, so the legend carries the mapping, and every member needs a `label`. A pair is the clearest form: an Out series with `color="neutral"` beside an In series with `color="neutral"` and `texture="hatch"` reads as the dark and light halves of one agent's traffic.

Below, the three us-east zones share blue, and `eu-west-1` takes its own color.

## Live data

Live values on a bar chart update in place: the categories are fixed, so bars never scroll. Each update morphs every bar from its current height to its new value with a per-datum tween, while the y axis glides to fit: the domain continuously chases its target and the value tick labels fade between tick sets instead of popping. `prefers-reduced-motion` snaps every update instantly. When the live dimension is time (a sliding window of appends), reach for a [`LineChart`](/components/charts/line-chart) or [`AreaChart`](/components/charts/area-chart) instead: bars at every timestamp read as categories, not a stream.

When the categories change (a sliding window of buckets, for example), the bars snap to their new values, and the y axis still glides. Motion plays only while the chart is on screen. A chart that is near the viewport but off screen paints each update settled, with no tween.

This demo recomputes all six regions every 400ms from a pure function of a tick counter (offset sine waves per region), so it renders deterministically; a real chart would replace `data` as new readings arrive.

<Example>
	<LiveBarChartExample />
</Example>

```tsx
import { BarChart } from "@ngrok/mantle/bar-chart";
import { useEffect, useState } from "react";

/** Deterministic values per tick: offset sine waves per region, no Math.random. */
function liveConnections(tick: number) {
	const regions = ["us-east", "us-west", "eu-west", "eu-central", "ap-southeast", "sa-east"];
	return regions.map((region, index) => ({
		region,
		connections: Math.round(
			900 + 460 * Math.sin(tick / 10 + index * 1.7) + 210 * Math.sin(tick / 3.6 + index * 0.9),
		),
	}));
}

function LiveBarChartExample() {
	const [tick, setTick] = useState(0);

	useEffect(() => {
		const interval = setInterval(() => {
			setTick((current) => current + 1);
		}, 400);
		return () => clearInterval(interval);
	}, []);

	return (
		<BarChart.Root
			data={liveConnections(tick)}
			xKey="region"
			aria-label="Live connections by region"
		>
			<BarChart.Grid />
			<BarChart.XAxis />
			<BarChart.YAxis />
			<BarChart.Bar dataKey="connections" label="Connections" color="blue" />
			<BarChart.Tooltip />
		</BarChart.Root>
	);
}
```

## Lists of charts

A page of 100 charts pays for the handful a reader can see. A dormant `BarChart.Root` is a shell: the plot box, the named interaction overlay, and its screen-reader description. It holds no paint surface and no engine until it comes within one viewport of the visible area, takes focus, or prints; then it activates outside React, in slices of a few milliseconds that yield between them, on-screen charts first, and paints in the task that activates it. A print paints every chart settled, with tick labels and gridlines at full opacity. The hover layers and the tooltip surface mount on the first hover, and the screen-reader data table waits for focus alone: it mounts once a reader tabs into the chart, so a page of sparklines holds no hidden tables until a reader asks for one. Add `content-visibility: auto` to your list's cards as a complement: it skips style and layout for offscreen cards, and the chart's own gate already skips paint.

Wrap a list of interactive charts in [`BarChart.List`](#barchartlist). The charts inside share one `role="status"` live region, so a page of 100 charts mounts one region instead of one per chart, plus one for each `BarChart.CopyButton`. Each chart keeps its own tooltip, description, and data table. Charts of different families can share one List, so one `BarChart.List` can hold a grid of bar, line, area, and scatter charts. A [static chart](#static-charts) has no tooltip and no live region, so a list of sparklines needs no List.

The mount cost of a list is measured, not assumed. The [chart mount benchmark](/bench/charts?animate=0&kind=bar&mode=table&n=100&points=30) renders a `DataTable` of 100 rows with two sparklines each; `mode=list` renders cards of full charts, and `n`, `kind`, and `points` set the shape. The Playwright driver in `apps/www/bench/` loads the page and reports main-thread time, long tasks, and frames per case.

## Modes

`mode` sets how much of the chart's contract a Root exposes. Pick by what a reader does with the chart.

| `mode`                    | Use it for                                                                                                                         | A reader gets                                                                                                                                          |
| :------------------------ | :--------------------------------------------------------------------------------------------------------------------------------- | :----------------------------------------------------------------------------------------------------------------------------------------------------- |
| `"interactive"` (default) | A chart a reader explores: a dashboard panel, a detail page, a report with a question behind it.                                   | A named `role="application"` Tab stop, hover and keyboard point cursor, a tooltip readout, polite announcements, and an sr-only data table on focus.   |
| `"static"`                | A chart a reader glances at while the exact values sit beside it: a sparkline in a table row or a card, a trend in a print report. | A named `role="img"` with a text description (kind, count, range, series), no Tab stop, no hover, no tooltip, no table. `animate` defaults to `false`. |
| `"decorative"`            | A placeholder whose values are not information: synthetic bars behind an empty state, a hero backdrop.                             | Nothing: hidden from assistive technology, out of the tab order, inert, every series in one neutral fill.                                              |

Noninteractive is not decorative. A sparkline beside a total still tells a reader when activity happened and how it varied, so it keeps a name and a description; only its values live in the text beside it. One hundred sparklines in a table as one hundred Tab stops is a focus order no reader wants, and a readout that only a pointer can reach fails WCAG 2.2 SC 2.1.1 (Keyboard), so `"static"` offers neither. A chart that is the only source of its values stays `"interactive"`.

### Static charts

Set `mode="static"` for a chart a reader glances at while the exact values sit beside it. The plot is a named `role="img"`: it takes the same `aria-label` or `aria-labelledby` an interactive chart does, and its `aria-describedby` points at the description, so a screen reader hears the chart kind, the category count, the first and last category, and the series labels without a Tab stop. There is no interaction overlay: no hover band, no tooltip, no keyboard point cursor, no data table, and no live region, and a composed `BarChart.Tooltip` has no effect. Pointer events pass through to the row or card behind it. The series keep their colors. `animate` defaults to `false`, because a list of sparklines that each play a reveal as the reader scrolls is motion with no information in it; pass `animate` to play the reveal. The interaction props (`activeIndex`, `onActiveIndexChange`, `onDatumActivate`) are forbidden at the type level. The [Sparklines in a List](/recipes/sparklines-in-a-list) recipe is the worked example.

```tsx
<div className="flex items-center gap-2">
	<BarChart.Root
		data={service.requests}
		xKey="day"
		mode="static"
		aria-label={`Requests for ${service.name}, last 30 days`}
		className="aspect-auto h-6 w-28"
	>
		<BarChart.Bar dataKey="count" label="Requests" color="blue" />
	</BarChart.Root>
	<span className="text-muted text-xs tabular-nums">{compact(service.requestTotal)}</span>
</div>
```

### Decorative charts

Set `mode="decorative"` to render the chart as a placeholder backdrop instead of real data: synthetic bars behind an empty state, an atmospheric hero graphic. A decorative chart keeps its visual rendering and animation but drops every layer that only makes sense for real data: it is hidden from assistive technology, removed from the tab order, and inert to pointer and keyboard, with no hover band, tooltip, sr-only data table, or live region. Because the values aren't information, `mode="decorative"` is mutually exclusive with the accessible-name props (`aria-label` / `aria-labelledby`) and the interaction props (`activeIndex`, `onActiveIndexChange`, `onDatumActivate`); the type won't compile with both.

A decorative chart also drops the series colors. Every series paints `--color-chart-decorative`, one neutral fill that outranks a series' `color`. A backdrop carries no series identity, and a hue on values that are not information invites a reader to decode it.

**That fill is what keeps an overlaid message readable.** `Empty.Description` sits on `text-muted`, which measures 4.88:1 on a bare light card (0.38 over the 4.5:1 floor for 14px text), so any tint under that copy spends the headroom. `--color-chart-decorative` is the darkest neutral step that still clears the floor in both themes: 4.56:1 in light and 4.93:1 in dark. The message needs no scrim behind it, no dimming, and no blur. Redeclare the token on the Root to retune the fill (`className="[--color-chart-decorative:var(--color-neutral-100)]"`) and re-measure the copy against the value you pick.

Reach for `mode="decorative"` over hand-rolled `inert` + CSS: it removes the interaction overlay at the source, so consumers never target chart internals to neutralize it. Keep the real empty-state message as a sibling of the chart (not inside it) so screen readers still announce it; the decorative chart itself is silent.

`mode="decorative"` says the values are not information; it is not a `disabled` flag (a chart is not a form control). For real data a reader only glances at, use [`mode="static"`](#static-charts).

</Example>

## Color and accessibility

Design the chart to look right first. Then get as close to accessible as you can, and say plainly where a choice falls short. A chart that follows every contrast rule to the letter can turn noisy, so mantle documents the guidance and its exemptions and forbids no color. This section is the reference for every chart family: bar, line, area, and scatter.

### What WCAG asks of a chart

[WCAG 2.2 SC 1.4.11 Non-text Contrast](https://www.w3.org/WAI/WCAG22/Understanding/non-text-contrast.html) asks for 3:1 against adjacent colors for the "parts of graphics required to understand the content". Bars, slices, lines, and points are those parts. Text has its own rule (SC 1.4.3, 4.5:1).

- A mark needs 3:1 against the surface behind it.
- Lines need 3:1 against their background. They "do not need to contrast with each other or the graduated lines", so two lines of close colors pass if each one clears the background.

Two things exempt a mark, because they make it no longer required to understand the content:

- The same values in another form a sighted reader can see: text labels on or beside the marks, or a table the reader can open. W3C's example is a table that shows when the reader presses a "Long Description" button.
- A darker border around a low-contrast mark. W3C's pie chart example adds "a darker border … around the yellow slice".

Two things do not exempt a mark:

- A hover tooltip. "The unfocused default version must already have sufficiently contrasting colors or text."
- Mantle's own data table. The tooltip and the sr-only data table carry every value, but the table is for screen readers. A sighted reader with low vision never sees it, so it does not exempt the marks.

### What mantle measures

Each color name paints its `--color-chart-<name>` token: the color's 600 step in light mode and its 500 step in dark mode (the 500 step reads washed out on white). Mantle measures every name against the card surface in both themes, in `chart/tokens.test.ts`:

| Theme   | Names under 3:1 on the card |
| ------- | --------------------------- |
| `light` | `yellow` (2.94:1)           |
| `dark`  | none                        |

The color choices are yours. Mantle does not promise that any set of names stays apart for a reader with a color vision deficiency. Two habits help:

- Pick colors that differ in lightness as well as hue. Blue beside emerald differs mostly in hue; blue beside amber differs in lightness too.
- Add a second encoding when series sit side by side: `texture` on bars, [`shape`](/components/charts/scatter-plot#point-shapes) on points.

### Keep a chart to eight series

Show the top seven series, plus one "Other" series that sums the tail and wears `color="neutral"`. Other is always neutral, so it reads as the tail and not as one more series. [When to use](#when-to-use) has a worked fold. When several series belong to one thing, they can share one color and stay apart by texture; see [Sharing one color](#sharing-one-color).

### When a color falls short

`yellow` in light mode sits under 3:1, and so can a brand color you pass as a CSS string. If a chart needs one of them, use one or more of these:

- Put the color on a fill, not a thin line. A bar or a stacked segment is easier to see than a 2px line at the same contrast.
- Show the values as visible text beside the marks: a total, a label, or a [`DataTable`](/components/data-display/data-table) the reader can open. Visible values exempt the marks.
- Add a `texture` (bars) or a `shape` (points), so the reader does not need the color to tell that series from the others.

## Accessibility

Every interactive chart must have an accessible name: either a direct `aria-label` or an `aria-labelledby` reference to a visible title. This is enforced at the type level: `BarChart.Root` does not compile without exactly one of the two. Prefer `aria-labelledby` when the chart sits under a visible heading, so the name never drifts from the title. The name lands on the focusable interaction overlay, the chart's single named element (the paint surface itself is hidden from assistive technology, so the chart is never announced twice). A [static chart](#static-charts) names its plot `role="img"` instead and has no Tab stop. A [decorative chart](#decorative-charts) carries no real data, so it takes no accessible name and is hidden from assistive technology entirely.

The chart is a single Tab stop with a full keyboard model:

- **Left / Right arrows** step between categories. On a horizontal chart, **Down / Up arrows** step too.
- **PageUp / PageDown** jump forward and back in larger strides (about a tenth of the data). On a horizontal chart, **PageDown** jumps forward and **PageUp** jumps back.
- **Home / End** jump to the first and last category.
- **Escape** clears the active category.
- **Enter / Space** activate the current category (fires `onDatumActivate`). A held key activates once.

Escape, Enter, and Space act only while a category is active. An idle Escape therefore reaches the surface around the chart, such as a panel that closes on Escape. A chord with Alt, Ctrl, or Meta passes through to the browser. In forced-colors mode, the focused chart shows a focus outline, and the hover band stays visible.

Keyboard stepping announces the category and each series' value through a debounced `aria-live="polite"` region, so rapid arrowing doesn't flood the screen-reader queue. Announcements follow keyboard steps only: the chart doesn't announce a data update while the keyboard cursor rests on a category. When the `labelFormat` or `valueFormat` of a composed `BarChart.Tooltip` returns a string or a number, the announcement uses it. A stacked chart announces the Total before the series values. The data table keeps the default number format.

The overlay's `aria-describedby` points at a screen-reader description, `data-slot="bar-chart-description"`, so a screen reader hears what the chart holds when it takes focus: the chart kind, the number of categories, the first and last category, the series labels, and the keyboard instructions. For example: "Bar chart with 12 categories from Jan to Dec. Series: Desktop, Mobile. Use the left and right arrow keys to move between data points, …". An empty chart reads "Bar chart with no data." in place of the count and range. Server HTML carries the plain count alone. The range waits for hydration, because `Intl` output differs by locale, and the series labels register in layout effects, so both render on the client.

`BarChart.Root` mounts dormant and renders its sr-only data table (the category column plus one column per series) once it engages: once focus lands inside it (the overlay is the Tab stop, and a focusable part composed inside the Root, such as `BarChart.CopyButton`, counts too). It never goes dormant again. Visibility paints the chart but never mounts the table. The table is bounded to the first 150 rows, with a caption stating the summarization when the data is longer. The Root stamps `data-state="dormant"`, then `data-state="engaged"`, and the table mounts with the flip, so a screen reader's table list names only the charts the reader has focused. The description above names what every chart holds, focused or not. Tooltips enhance, they never gate, and no part removal can strip keyboard access to the data. The keyboard point cursor steps one category at a time, so it reaches every category. When the chart holds 4 or more categories per device pixel of plot width, each arrow key press moves one device-pixel column. The cursor then reaches one category per column. The table holds the first 150 rows, and `BarChart.CopyButton` copies every row.

The table doubles as the chart's machine-readable surface: value cells carry the raw number in `data-value` (and date row headers, where present, the exact ISO timestamp in `<time dateTime>`), so agents and scrapers read precise data from the DOM without reverse-engineering locale formatting. Assistive tech still hears the human-formatted text, and the table itself is addressable at `data-slot="bar-chart-data-table"`. To reach it, an agent focuses the chart (a scroll into view is not enough), then waits for `data-state="engaged"` on the Root. `BarChart.CopyButton` hands over the same rows as markdown with neither step.

### Accessibility limits

Every chart family (bar, line, area, and scatter) has these limits:

- A live chart has no pause control. Add one to the page: WCAG 2.2 SC 2.2.2 (Pause, Stop, Hide) asks for a way to pause, stop, or hide content that updates by itself.
- Point `aria-labelledby` at the title element, not at a container that holds the chart. A container's text includes the chart's own description and data table, so the name would repeat them.
- When you set `pending`, announce the refresh yourself. The chart dims the plot and tells assistive technology nothing.
- On a touch screen, a tap shows the readout only while the finger is down, and the same tap fires `onDatumActivate`.
- A `BarChart.CopyButton` and a legend that scrolls each add one Tab stop.
- Inside a mantle [`Dialog`](/components/overlays/dialog) or [`Sheet`](/components/overlays/sheet), Escape closes the dialog even when a readout is open.
- Escape dismisses the readout only while the chart's overlay has focus. A readout that a pointer hover alone opened stays until the pointer leaves.
- The 3D rotation of a [`ScatterPlot`](/components/charts/scatter-plot#accessibility) is pointer-only and needs a drag.

## API Reference

`BarChart.Bar`, `BarChart.Grid`, `BarChart.XAxis`, `BarChart.YAxis`, and `BarChart.ReferenceLine` are renderless: they register configuration with the Root, which paints everything on one surface: an `<svg>`. They accept no `className` or other DOM props. `BarChart.Tooltip` and `BarChart.Legend` accept div props — the tooltip forwards them to the readout element the Root owns, and the legend renders real DOM in flow below the plot. `BarChart.CopyButton` also renders real DOM — an icon button accepting `button` props. `BarChart.List` renders a `div` around a list of Roots.

### BarChart.Bar

One bar series. Renders nothing itself — it registers the series with the chart, which paints it. Compose one `Bar` per series; with `stacked` on the Root, bars stack from the baseline up in registration order. Accepts no `className` or DOM props.

**Bar thickness follows the category spacing; there is no `barSize` prop.** Bars fill their category step except for a fixed 2px gap between neighbors. As steps narrow, the gap drops to 1px, then to none. On a wide step, a cap holds: a bar fills its slot up to 60% of one category's step, floored at 24px and ceilinged at 64px. Few categories therefore grow the bars rather than the air between them: seven days across a 93px step paint ~56px bars, not 24px bars in 69px of air. Grouped series split the band and each bar fills its own slot, so a group tightens instead of outgrowing its category. The rule reads the step alone, so the same data at the same width always paints the same pixels, and thickness only ever rises as categories thin out.

A bar, or a whole stack, rounds both of its ends at 2px. Stacked segments sit 1px apart. A chart with no axis and no grid runs its bars edge to edge, with 12% headroom over the tallest bar and no zero rule, so it reads as a sparkline.

| `label?` | `string`      |                         | A short label painted above the line's right end. |
| `color?` | `SeriesColor` | neutral reference color | Line color.                                       |

### BarChart.Tooltip

Customizes the hover/keyboard tooltip readout. The tooltip itself is part of `BarChart.Root`'s interaction contract and renders even when this part is absent — compose it to format the label or values, append a footer, or replace the content entirely.

A `children` readout renders inside a `<div data-slot="bar-chart-tooltip-label">`. When it goes away, React removes that div instead of your own text nodes: a browser translation engine reparents text nodes, and a removal aimed at one throws. The div is `display: contents`, so it adds no box and your content stays a direct layout child of the parent. To style it as a box, set a display of your own on it first. [Browser translation](/browser-translation) covers the mechanism and the rules your own components need.

The `HoverSnapshot` passed to `footer` and `children` describes the active category: `{ index, xValue, datum, points, viaKeyboard }`, where `points` lists every series' value at the active index. Stacked, the rows run from the far end of the pile back to the baseline; unstacked, they follow registration order.

All props from [div](https://developer.mozilla.org/en-US/docs/Web/HTML/Element/div#attributes) (forwarded to the tooltip element the Root owns) except `children`, plus:

| Prop           | Type                                                    | Default  | Description                                                             |
| -------------- | ------------------------------------------------------- | -------- | ----------------------------------------------------------------------- |
| `labelFormat?` | `(value: string \| number \| Date) => ReactNode`        |          | Format the x/label row of the readout.                                  |
| `valueFormat?` | `(value: number, dataKey: string) => ReactNode`         |          | Format each series value.                                               |
| `indicator?`   | `"line" \| "none"`                                      | `"line"` | The per-series color key: a short stroke (default) or nothing.          |
| `footer?`      | `ReactNode \| ((snapshot: HoverSnapshot) => ReactNode)` |          | Extra content appended below the series rows (e.g. a "view logs" hint). |
| `children?`    | `(snapshot: HoverSnapshot) => ReactNode`                |          | Replace the entire readout.                                             |

**Data attributes**

| Data Attribute | Value                       | Description                                                                 |
| -------------- | --------------------------- | --------------------------------------------------------------------------- |
| `data-slot`    | `"bar-chart-tooltip-label"` | On the `<div>` wrapping a `children` readout. The default readout has none. |

### BarChart.Legend

The legend: series names keyed by color swatches, rendered as real DOM in flow below the plot. Always compose it on multi-series charts — identity must never rely on color-matching alone. It renders nothing for a single series (the chart's title already names it). The legend is at most 64px tall (`max-h-16`) and scrolls past that, so many series never take the plot's height in a fixed-height Root. Set a `max-h-*` class in `className` to change the bound.

A `children` render prop renders inside a `<div data-slot="bar-chart-legend-label">`. When it goes away, React removes that div instead of your own text nodes: a browser translation engine reparents text nodes, and a removal aimed at one throws. The div is `display: contents`, so it adds no box and your content stays a direct layout child of the parent. To style it as a box, set a display of your own on it first. [Browser translation](/browser-translation) covers the mechanism and the rules your own components need.

All props from [div](https://developer.mozilla.org/en-US/docs/Web/HTML/Element/div#attributes) except `children`, plus:

| Prop        | Type                                  | Default | Description                                                       |
| ----------- | ------------------------------------- | ------- | ----------------------------------------------------------------- |
| `children?` | `(series: SeriesMeta[]) => ReactNode` |         | Replace the default legend items; receives the registered series. |

**Data attributes**

| Data Attribute | Value                                                                                                        | Description                                                                                                                                                           |
| -------------- | ------------------------------------------------------------------------------------------------------------ | --------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `data-slot`    | `"bar-chart-legend"`                                                                                         | The legend list. `BarChart.Legend` renders it in flow below the plot.                                                                                                 |
| `data-slot`    | `"bar-chart-legend-label"`                                                                                   | On the `<div>` wrapping a `children` render prop. The default legend has none.                                                                                        |
| `data-texture` | `"solid" \| "hatch" \| "hatch-reverse" \| "crosshatch" \| "perpendicular" \| "parallel" \| "grid" \| "dots"` | On each series' swatch, naming the `texture` its [BarChart.Bar](#barchartbar) registered. The swatch paints the pattern itself, so target this only to restyle a key. |

### BarChart.CopyButton

A button that copies the chart's current data to the clipboard as a GitHub-flavored markdown table: the category column plus one column per series in paint order. Values are machine-stable — plain un-separated numbers, an em dash for gaps — so the paste target receives parseable data, not locale formatting. Renders an icon button in flow where composed; `Root` is relatively positioned, so `className` can dock it over a corner (e.g. `absolute right-0 top-0`).

All props from [button](https://developer.mozilla.org/en-US/docs/Web/HTML/Element/button#attributes), plus:

| Prop           | Type                       | Default                   | Description                                                                    |
| -------------- | -------------------------- | ------------------------- | ------------------------------------------------------------------------------ |
| `label?`       | `string`                   | `"Copy data as Markdown"` | The accessible name, rendered as the button's `aria-label`.                    |
| `onCopy?`      | `(value: string) => void`  |                           | Callback fired after a successful copy, passes the serialized markdown.        |
| `onCopyError?` | `(error: unknown) => void` |                           | Callback fired when an error occurs during copying.                            |
| `asChild?`     | `boolean`                  | `false`                   | Compose the copy behavior onto your own element instead of the default button. |

While a copy is fresh, an always-mounted `role="status"` element beside the button announces "Copied" to a screen reader.

| Data Attribute | Value                     | Description                  |
| -------------- | ------------------------- | ---------------------------- |
| `data-slot`    | `"bar-chart-copy-button"` | The button the part renders. |

### BarChart.List

Groups a list of charts, such as one chart per card, so they share one `role="status"` live region. A page of 100 charts mounts one region instead of one per chart, plus one for each `BarChart.CopyButton`. Each chart keeps its own tooltip, description, and data table. Charts of different families can share one List. See [Lists of charts](#lists-of-charts).

Renders a `div` (`bar-chart-list`) that holds the charts in a `display: contents` wrapper (`bar-chart-list-items`), so a grid or flex layout on the List reaches the cards, and the live region as its last child. `BarChart.List` takes no `asChild`: a list element such as `ul` cannot hold the live region as a child.

All props from [div](https://developer.mozilla.org/en-US/docs/Web/HTML/Element/div#attributes).

| Data Attribute | Value                    | Description                                                                                                 |
| -------------- | ------------------------ | ----------------------------------------------------------------------------------------------------------- |
| `data-slot`    | `"bar-chart-list"`       | The List wrapper, with any forwarded chain ahead of it. It takes the `className` and the other div props.   |
| `data-slot`    | `"bar-chart-list-items"` | The `display: contents` wrapper around the charts, so a grid or flex layout on the List lays out the cards. |

### Chart color tokens

Every mantle color name has one chart token, `--color-chart-<name>`, and a series with `color="<name>"` paints it. The legend swatch and the tooltip stroke paint the same token.

| CSS Variable                 | Description                                                                                                                                                                                                                                                                                         |
| ---------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `--color-chart-<hue>`        | One per hue: `amber`, `blue`, `cyan`, `emerald`, `fuchsia`, `gray`, `green`, `indigo`, `lime`, `orange`, `pink`, `purple`, `red`, `rose`, `sky`, `teal`, `violet`, and `yellow`. Light mode paints the hue's 600 step and dark mode its 500 step, because the 500 step reads washed out on white.   |
| `--color-chart-<functional>` | One per functional name, as an alias of the hue its status color uses: `accent` and `info` paint `sky`, `danger` paints `rose`, `important` paints `purple`, `success` paints `emerald`, and `warning` paints `amber`. `neutral` paints `neutral-600` in light mode and `neutral-500` in dark mode. |
| `--color-chart-decorative`   | The neutral fill every series wears on a [decorative chart](#decorative-charts), in place of its own color.                                                                                                                                                                                         |

[Color and accessibility](#color-and-accessibility) lists what each name measures against the card. A series that _means_ good or bad (an error rate, pass and fail) wears a functional name such as `danger` or `success`.

The `color` prop also takes any CSS color string as an escape hatch. A static color (a raw hex) does not adapt across themes, so prefer a per-theme `var(--token)`, and measure it against the card and against the other colors on the chart yourself.

#### Restyle a color name

Two public paths change what a series paints:

- **One series:** pass a different `color` on `BarChart.Bar`, a color name or any CSS color string.
- **One chart:** redeclare the token on `BarChart.Root`: `className="[--color-chart-blue:var(--color-brand)]"`. Every series on that chart with `color="blue"` picks the new value up. So do its legend swatch and tooltip stroke.

The chart paints every token as CSS, so the browser resolves it inside the Root's own cascade, with no computed-style read and no hidden probe element. A declaration scoped to one Root wins for that chart alone, and sibling charts on the page keep the theme value. Declare the same custom property higher up (on a dashboard wrapper, or at `:root`) to retheme a whole subtree.

Both paths want a `var()` reference rather than a raw hex, for the reason [Brand colors](#brand-colors) gives. A restyled name leaves mantle's measurements behind, so the measurement is yours. The `#d07c00` below measures 3.19:1 on the light card surface.

```tsx
import { BarChart } from "@ngrok/mantle/bar-chart";

const monthlyVisitors = [
	{ month: "January", desktop: 186, mobile: 80 },
	{ month: "February", desktop: 305, mobile: 200 },
	{ month: "March", desktop: 237, mobile: 120 },
	{ month: "April", desktop: 73, mobile: 190 },
	{ month: "May", desktop: 209, mobile: 130 },
	{ month: "June", desktop: 214, mobile: 140 },
];

function SeriesIdentityBarChartExample() {
	return (
		// An app declares its brand token once, high in the tree. This example
		// declares it on the wrapper so it stands alone. A theme that needs its own
		// value takes a variant: `dark:[--color-brand:…]`.
		<div className="grid w-full gap-6 [--color-brand:#d07c00] sm:grid-cols-2">
			<BarChart.Root
				data={monthlyVisitors}
				xKey="month"
				className="[--color-chart-blue:var(--color-brand)]"
				aria-label="Visitors by month, blue restyled"
			>
				<BarChart.Grid />
				<BarChart.XAxis tickFormat={(month) => String(month).slice(0, 3)} />
				<BarChart.YAxis />
				<BarChart.Bar dataKey="desktop" label="Desktop" color="blue" />
				<BarChart.Bar dataKey="mobile" label="Mobile" color="emerald" />
				<BarChart.Legend />
			</BarChart.Root>
			{/* The sibling never sees the declaration above, so its Desktop series
			    keeps the theme blue. */}
			<BarChart.Root
				data={monthlyVisitors}
				xKey="month"
				aria-label="Visitors by month, one color overridden"
			>
				<BarChart.Grid />
				<BarChart.XAxis tickFormat={(month) => String(month).slice(0, 3)} />
				<BarChart.YAxis />
				<BarChart.Bar dataKey="desktop" label="Desktop" color="blue" />
				<BarChart.Bar dataKey="mobile" label="Mobile" color="var(--color-brand)" />
				<BarChart.Legend />
			</BarChart.Root>
		</div>
	);
}
```
