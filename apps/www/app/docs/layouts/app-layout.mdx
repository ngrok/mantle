<PageHeader id="app-layout">App Layout</PageHeader>

A viewport-locked application shell. The shell itself never scrolls: `AppLayout.Content` is a rounded card
holding a toolbar and a page region, and `AppLayout.Body` (the page region) is the only scroll container
in the whole shell and its `main` landmark, with `overscroll-none` so long pages never bounce or drag the chrome. Above it,
`AppLayout.Header` is a toolbar row with three slots: the sidebar trigger, the breadcrumb trail, and the
page's actions. It sits beside the scroll container, so it stays pinned without `sticky`. `AppLayout.Notice` is a full-window composition slot for
app-wide messaging that pushes everything (including any sidebar) down. It can stack a rare maintenance or
environment banner with a persistent account-alert bar. It is a **layout**: it owns _where things go_, and
app state (routing, sessions, data) never enters it.

The card reads the same way as every other mantle surface (`Content` wrapping `Header` + `Body`), which is
exactly the shape of the column beside it (`Sidebar.Nav`) and of
[`Dialog.Content`](/components/overlays/dialog), [`Sheet.Content`](/components/overlays/sheet), and
[`Card.Root`](/components/data-display/card).

The canonical composition pairs the shell with the [Sidebar](/components/navigation/sidebar). The two are
deliberately decoupled (`AppLayout` never references sidebar state) but cohesive: wrap the shell in
`Sidebar.Root`, place `Sidebar.Nav` as the first child of `AppLayout.Workspace`, and put `Sidebar.Trigger`
in `AppLayout.HeaderStart`. The
[collapsed icon rail](/components/navigation/sidebar#collapsing-to-the-icon-rail) is entirely the sidebar's
business: the shell markup does not change, and the rail shares the shell's `bg-base` surface, so the card
gutter shows no seam. Every row here is wrapped in
[`Sidebar.Tooltip`](/components/navigation/sidebar#sidebartooltip), which is what labels the rail for
pointer users once it collapses; it needs a `TooltipProvider` ancestor, which a real app mounts at its root.
The demo runs in its own framed document, exactly like a real app: collapse
the sidebar to its icon rail with the trigger (or <kbd translate="no">⌘B</kbd>/<kbd translate="no">Ctrl+B</kbd>; the shortcut binds to
the frame, not this page), hover a row to see its tooltip, and reopen it the same way, toggle the
notice to see the strip push the whole shell (sidebar included) down, and switch the preview to the mobile
viewport for the sheet presentation. The sidebar's footer stays put through all of it: the account-scoped
rows every product shares, a **Help** menu row, and the account switcher row. The same sidebar can also show
a second **section** of navigation:
choose **Account settings** from that account menu and the header's product
switcher becomes a back link while the body swaps to the settings nav: the shell markup is identical, the
`<nav>` landmark renames itself, the icon rail keeps working, and the back link returns to the product page
you left. The demo narrows the sidebar's `mobileBreakpoint` to `md`
so the desktop panel survives the preview's desktop and tablet widths; ngrok's dashboards keep the `lg`
default.

```tsx
/**

/**
 * The sidebar header while the settings section is showing: one full-width row
 * that leaves the section, in the same header band the product switcher owns the
 * rest of the time. The whole row is the affordance, so it is a single
 * `Sidebar.ItemButton` that collapses to the arrow chip on the icon rail.
 */
function SettingsHeader({
	onBack,
	returnLabel,
	returnPath,
}: {
	onBack: () => void;
	returnLabel: string;
	returnPath: string;
}) {
	return (
		<Sidebar.Tooltip label={`Settings, back to ${returnLabel}`}>
			<Sidebar.ItemButton asChild className="font-medium">
				<a
					href={returnPath}
					onClick={(event) => {
						event.preventDefault();
						onBack();

				>
					<ArrowLeftIcon />
					<span className="text-strong min-w-0 flex-1 truncate text-base">Settings</span>
					{/* keeps the accessible name from being a bare "Settings" link inside
					    the Settings navigation */}
					<span className="sr-only">, back to {returnLabel}</span>
				</a>
			</Sidebar.ItemButton>
		</Sidebar.Tooltip>
	);
}

/** Whichever navigation section is showing — a product's pages, or settings. */
function ShellNav({

	pathname,
	sections,

			))}
		</>
	);
}

/** One page-level action, described once so the icon buttons and the mobile menu stay in step. */
type PageAction = {
	label: string;
	icon: ReactNode;
	onSelect: () => void;
};

/**
 * The header's page actions: one icon button per action from `md` up, and one
 * menu behind a single icon button below it. Both controls are in the HTML and
 * CSS picks one, so the server paints the right control and hydration swaps
 * nothing. The menu's items mount when the menu opens. The `md` breakpoint
 * matches this demo's `mobileBreakpoint`.
 */
function PageActions({ actions }: { actions: ReadonlyArray<PageAction> }) {
	return (
		<>
			{/* display: contents from md up, so the buttons sit in the slot's own gap */}
			<div className="hidden md:contents">
				{actions.map((action) => (
					<Tooltip.Root key={action.label}>
						<Tooltip.Trigger asChild>
							<IconButton
								type="button"
								appearance="outlined"
								intent="neutral"
								size="sm"
								icon={action.icon}
								label={action.label}
								onClick={action.onSelect}
							/>
						</Tooltip.Trigger>
						<Tooltip.Content>{action.label}</Tooltip.Content>
					</Tooltip.Root>
				))}
			</div>
			<DropdownMenu.Root>
				<DropdownMenu.Trigger asChild>
					<IconButton
						type="button"
						appearance="outlined"
						intent="neutral"
						size="sm"
						className="md:hidden"
						icon={<DotsThreeIcon />}
						label="More actions"
					/>
				</DropdownMenu.Trigger>
				<DropdownMenu.Content align="end">
					{actions.map((action) => (
						<DropdownMenu.Item key={action.label} className="gap-2" onSelect={action.onSelect}>
							{action.icon}
							{/* an element, not bare text: a swapped icon then inserts before a node React still owns on a translated page */}
							<span>{action.label}</span>
						</DropdownMenu.Item>
					))}
				</DropdownMenu.Content>
			</DropdownMenu.Root>
		</>
	);
}

export function Shell() {
	// the framed examples fake a router so they can be embedded; a real app
	// renders react-router `Link`s through `asChild` and derives both `current`
	// and which section is showing from `useLocation()`. The rows'
	// `Sidebar.Tooltip`s need a `TooltipProvider` ancestor — the docs site mounts
	// one at its root, so mount one at yours too.
	const [pathname, setPathname] = useState("/endpoints");
	// where the settings section's back link returns to: the product page you
	// left. A real app reads this from router history or a fixed section parent.
	const [returnPath, setReturnPath] = useState("/endpoints");
	const [productId, setProductId] = useState(products[0].id);
	const [accountId, setAccountId] = useState(accounts[0].id);
	const [showNotice, setShowNotice] = useState(false);
	const [alertExample, setAlertExample] = useState<"single" | "multiple" | null>(null);
	const [dismissed, setDismissed] = useState<ReadonlySet<string>>(new Set());
	const dismiss = (id: string) => setDismissed((previous) => new Set(previous).add(id));
	// Choosing a preset (or toggling it off) also restores dismissed alerts,
	// so the alert buttons double as a reset.
	const chooseAlertExample = (example: "single" | "multiple") => {
		setDismissed(new Set());
		setAlertExample((current) => (current === example ? null : example));
	};
	// A real shell derives these from the matched route chain; see the
	// "Header Actions from Routes" recipe.
	const headerActions: ReadonlyArray<PageAction> = [
		{
			label: "Toggle notice",
			icon: <MegaphoneIcon />,
			onSelect: () => setShowNotice((current) => !current),
		},
		{ label: "One warning", icon: <WarningIcon />, onSelect: () => chooseAlertExample("single") },
		{ label: "Three alerts", icon: <BellIcon />, onSelect: () => chooseAlertExample("multiple") },
	];

	// which navigation the sidebar shows is *derived* from the location, the same
	// thing a real app gets for free from a nested settings route
	const inSettings = isSettingsPath(pathname);
	const allItems = [
		...productSections.flatMap((section) => section.items),
		...settingsSections.flatMap((section) => section.items),
		...footerItems,
	];
	const currentLabel = allItems.find((item) => item.path === pathname)?.label ?? "Overview";
	const returnLabel = allItems.find((item) => item.path === returnPath)?.label ?? "the dashboard";

	// every navigation goes through here, so entering the settings section always
	// records the product page its back link returns to
	function navigate(path: string) {
		if (isSettingsPath(path) && !inSettings) {
			setReturnPath(pathname);
		}
		setPathname(path);
	}

	return (
		// the framed demo narrows the mobile breakpoint; most apps keep the "lg" default
		<Sidebar.Root mobileBreakpoint="md">
			<AppLayout.Root className="fixed inset-0">
				<SkipToMainLink />
				<AppLayout.Notice>
					{showNotice && (
						<div className="text-on-filled bg-rose-500 px-4 py-2 text-center text-xs">
							Preview notice
						</div>
					)}
					<AlertCenter.Root>
						<AlertCenter.Bar />
						<AlertCenter.Content />
						{alertExample === "multiple" && (
							<AlertCenter.Item id="billing" intent="danger">
								<Alert.Icon />
								<Alert.Content>
									<Alert.Title>
										A payment could not be processed <a href="/billing">Review billing</a>
									</Alert.Title>
								</Alert.Content>
							</AlertCenter.Item>
						)}
						{alertExample != null && !dismissed.has("usage-limit") && (
							<AlertCenter.Item id="usage-limit" intent="warning">
								<Alert.Icon />
								<Alert.Content>
									<Alert.Title>
										Your workspace is approaching its monthly usage limit{" "}
										<a href="/usage">Review usage</a>
									</Alert.Title>
									<AlertCenter.DismissIconButton onClick={() => dismiss("usage-limit")} />
								</Alert.Content>
							</AlertCenter.Item>
						)}
						{alertExample === "multiple" && !dismissed.has("member-limit") && (
							<AlertCenter.Item id="member-limit" intent="warning">
								<Alert.Icon />
								<Alert.Content>
									<Alert.Title>
										Your workspace is approaching its member limit{" "}
										<a href="/members">Review members</a>
									</Alert.Title>
									<AlertCenter.DismissIconButton onClick={() => dismiss("member-limit")} />
								</Alert.Content>
							</AlertCenter.Item>
						)}
					</AlertCenter.Root>
				</AppLayout.Notice>
				<AppLayout.Workspace>
					{/* the landmark is renamed with the section it is showing */}
					<Sidebar.Nav aria-label={inSettings ? "Settings" : "Main"}>
						<Sidebar.Header>
							{inSettings ? (
								<SettingsHeader
									returnLabel={returnLabel}
									returnPath={returnPath}
									onBack={() => setPathname(returnPath)}
								/>
							) : (
								<ProductSwitcher productId={productId} onProductChange={setProductId} />
							)}
						</Sidebar.Header>

						<Sidebar.Body>
							<ShellNav
								sections={inSettings ? settingsSections : productSections}

										</a>

								</Sidebar.Tooltip>

							<Sidebar.Separator />
							<AccountSwitcher
								accountId={accountId}
								onAccountChange={setAccountId}
								onNavigate={navigate}
							/>
						</Sidebar.Footer>
					</Sidebar.Nav>

					<AppLayout.Content>
						<AppLayout.Header>

								<Sidebar.Trigger />
							</AppLayout.HeaderStart>

											<>
												<Breadcrumb.Item>
													<Breadcrumb.Link

														onClick={(event) => {
															event.preventDefault();
															navigate(settingsSectionPath);
```

## Composition

```text showLineNumbers=false
AppLayout.Root
├── AppLayout.Notice
└── AppLayout.Workspace
    └── AppLayout.Content
        ├── AppLayout.Header
        │   ├── AppLayout.HeaderStart
        │   ├── AppLayout.HeaderContent
        │   └── AppLayout.HeaderActions
        └── AppLayout.Body
```

- **`Root`** is the outer frame (`bg-base relative isolate flex h-full w-full flex-col overflow-clip`).
  It fills its nearest sized ancestor; merge `className="fixed inset-0"` to pin a real app shell to the
  viewport. The shell never scrolls; only `Body` does. It clips with `overflow-clip`, not `overflow-hidden`,
  for the same reason `Content` does: `hidden` **is** a scroll container that paints no scrollbar, so
  anything wider than the frame lets focus scroll the whole shell sideways. On a frame pinned with
  `fixed inset-0` that is the entire window, with no scrollbar and no gesture to bring it back.
- **`Notice`** is the full-window-width, vertical composition slot pinned above everything else
  (`flex w-full shrink-0 flex-col`). Stack a maintenance or environment banner and an account alert bar
  here; each brings its own colors while the slot pushes the whole shell down. Collapses to nothing when
  empty. Optional.
- **`Workspace`** is the region where the user works: everything below the notice, laid out as a flex row of
  columns (`flex min-h-0 flex-1`). Place a [`Sidebar.Nav`](/components/navigation/sidebar) (or any other
  rail, on either side) beside the `Content` card. The `min-h-0` is what lets `Body` scroll instead of the
  page. It owns **no gutter**, deliberately, so a rail stays flush against the window edge and a collapsed
  icon rail keeps its flush geometry.
- **`Content`** is the card surface: `bg-card border-card-muted relative m-(--app-layout-card-gutter,0.5rem) flex min-w-0 flex-1 flex-col
overflow-clip rounded-xl border shadow-sm`. It insets **itself** with its own margin
  (`--app-layout-card-gutter`), because the gutter has to belong to the card rather than to a wrapper: the
  only other element that could hold it also contains the rail. It does **not** scroll.
- **`Header`** is the toolbar row, `Content`'s **first child** (`flex h-14 shrink-0` with a hairline border
  beneath it). Its three slots hold the `Sidebar.Trigger`, the
  [Breadcrumb](/components/navigation/breadcrumb) trail, and the page's actions. It is `h-14` standalone; with a
  `Sidebar.Header` in the shell it derives its height from the sidebar's `--sidebar-header-height` token
  instead (the band that header's first row sits on), so the app switcher and the toolbar stay center-aligned
  as one row by construction, however many rows the sidebar header stacks below the band. It is
  pinned by `shrink-0`, not by `sticky`: it sits **outside** the scroll container, so it cannot scroll away,
  cannot be overlapped by a page's own `sticky top-0`, and does not steal height from a page asking for
  `h-full`. Optional standalone, but effectively **required** once you compose a `Sidebar` (see
  [Accessibility](#accessibility)).
- **`HeaderStart`**, **`HeaderContent`**, and **`HeaderActions`** are `Header`'s three slots, in that order.
  `HeaderStart` (`shrink-0`) holds the sidebar trigger, `HeaderContent` (`min-w-0 flex-1`) holds the breadcrumb
  trail and gives up width first, and `HeaderActions` (`ml-auto shrink-0`) holds the page's actions at the
  row's end. They carry the flex, so no call site sets it. See [Header slots](#header-slots).
- **`Body`** is the page region and the shell's **only** scroll container
  (`scrollbar relative min-h-0 w-full flex-1 overflow-y-auto overscroll-none`). Render your `<Outlet />`
  here. It is mantle's `Main` landmark by default (see [Landmarks](#landmarks)).
  See [Sizing a page to the card](#sizing-a-page-to-the-card) for what its classes buy you.
  There is deliberately **no `Footer` part**. A bar pinned to the bottom of the card is almost always a
  _page's_ bar (an editor's validity line, a save bar), and a route rendering through an `<Outlet />` inside
  `Body` could never reach a shell-level footer anyway, because it would be a sibling of the region the route
  renders into. Pin it inside `Body` instead:
  [Pinning a footer to the card](#pinning-a-footer-to-the-card).

## Polymorphism

Every part accepts an `asChild` prop. When `true`, the part renders its single child instead of its default
element, forwarding all class names, `data-*` attributes, and the ref onto that child.

All nine parts support it, and each has a reason a consumer would reach for it:

- **`AppLayout.Root`**: a `<form>` when the whole shell is one submission surface, or your own themed frame.
- **`AppLayout.Notice`**: an `<aside>` or a live region when the strip's content needs its own semantics.
- **`AppLayout.Workspace`**: rarely; swap it when the columns row needs a different element or a wrapper
  component of your own.
- **`AppLayout.Content`**: a `<section>` when the card is a labelled region of a larger document.
- **`AppLayout.Header`**: a real `<header>`, but only when the shell does _not_ own the `main` landmark (see
  [Accessibility](#accessibility) for why the default is a `<div>`).
- **`AppLayout.HeaderStart`**: rarely; the slot exists to carry `shrink-0`, and a control inside it brings its
  own element.
- **`AppLayout.HeaderContent`**: `Breadcrumb.Root` itself, so the trail's `<nav>` is the slot and the header
  holds one element fewer.
- **`AppLayout.HeaderActions`**: a `<form>` when every action submits the same form.
- **`AppLayout.Body`**: a plain `<div>` when the document already owns the `main` landmark: a docs demo, a
  test, a shell embedded in a page (see [Landmarks](#landmarks)).

## Header slots

`AppLayout.Header` is one flex row, and its three slots carry the flex. Compose them in order:

- **`AppLayout.HeaderStart`** is `shrink-0`: it takes only the width its children need and holds the row's
  start. `Sidebar.Trigger` goes here.
- **`AppLayout.HeaderContent`** is `min-w-0 flex-1`: it takes every pixel the other two slots leave and gives
  width back first. The [Breadcrumb](/components/navigation/breadcrumb) trail goes here, and `min-w-0` lets
  `Breadcrumb.List` scroll sideways instead of pushing the actions off the card.
- **`AppLayout.HeaderActions`** is `ml-auto shrink-0`: it takes only the width its children need, grows to
  the left as actions are added, and stays at the row's end even when the header renders no content slot.
  The page's actions go here, three at most.

The header's `gap-2` spaces the three slots. Each slot repeats it between its own children, so a second
control at the start or a second action at the end sits at the same spacing as the slots themselves. Grow the
trail below and watch it scroll inside the content slot while the two ends hold their width. The shell is
embedded and has no sidebar, so a back link takes the start slot that `Sidebar.Trigger` takes in an app shell.

## One header per page

> [!IMPORTANT]
> Every page in an app that renders `AppLayout` renders one `AppLayout.Header`, and that header holds at
> minimum `AppLayout.HeaderStart` with `Sidebar.Trigger` and `AppLayout.HeaderContent` with the route's
> breadcrumb trail. This is a hard requirement. The sidebar can collapse at every breakpoint, and
> `Sidebar.Trigger` is the only way back from a collapsed rail or a closed mobile sheet.

The canonical shell gives each route its header. The shell renders `AppLayout.Content` around its
`<Outlet />`, and each route renders `AppLayout.Header` and `AppLayout.Body` itself, so an action reads the
page's own state. There is no wrapper component. The route composes the mantle parts directly, and every
route repeats the three slots. The single-page demos on this page render the same two parts in the shell, and
the one other composition is the [deviation](#the-deviation-a-shell-owned-header) at the end of this section.

The shell renders the card and nothing inside it:

```tsx
// app/routes/app-shell.tsx
import { AppLayout } from "@ngrok/mantle/app-layout";
import { Sidebar } from "@ngrok/mantle/sidebar";
import { SkipToMainLink } from "@ngrok/mantle/skip-to-main-link";
import { Outlet } from "react-router";
import { AppSidebar } from "~/components/layout/app-sidebar";

export default function AppShell() {
	return (
		<Sidebar.Root>
			<AppLayout.Root className="fixed inset-0">
				<SkipToMainLink />
				<AppLayout.Workspace>
					<AppSidebar />
					<AppLayout.Content>
						<Outlet />
					</AppLayout.Content>
				</AppLayout.Workspace>
			</AppLayout.Root>
		</Sidebar.Root>
	);
}
```

A route renders its header, its actions, and its body:

```tsx

import { NewEndpointDialog } from "~/features/endpoints/new-endpoint-dialog";

export default function EndpointsPage() {
	const [dialogOpen, setDialogOpen] = useState(false);

	return (
		<>
			<AppLayout.Header>
				<AppLayout.HeaderStart>
					<Sidebar.Trigger />
				</AppLayout.HeaderStart>
				<AppLayout.HeaderContent>

						type="button"
						appearance="filled"
						intent="primary"
						size="sm"

					>
						New endpoint
					</Button>
				</AppLayout.HeaderActions>
			</AppLayout.Header>
			<AppLayout.Body>
```

`AppLayout.Body` is the `Main` landmark, so the skip link lands on the scrollport (see
[Landmarks](#landmarks)). The trigger and the trail remount on every navigation. Neither holds state, and the
sidebar's own state lives on `Sidebar.Root`, so nothing is lost.

### Keep Suspense inside the body

If a route suspends, put the boundary inside `AppLayout.Body`, around the page content, as the route above does.
A boundary above the header blanks the trigger and the trail until the data arrives, and a keyboard user
loses the only way back to the sidebar. React Router awaits a route module before it commits a navigation,
so only suspension inside the page component (a `use()` call, `useSuspenseQuery`, a lazy child) reaches a
boundary. Never wrap the shell's `<Outlet />` in a boundary whose fallback replaces the whole card.

### The deviation: a shell-owned header

A shell can render `AppLayout.Header` once, above its `<Outlet />`, and derive each route's actions from a
route handle. [Header Actions from Routes](/recipes/header-actions-from-routes) documents it. It is
secondary, and it costs something: the actions element renders outside the page, so it reads only the URL
and loader data, and a route whose action needs page state cannot use it. Pick it only when an app already
keeps its header in the shell and no route needs page state in its actions. Never mix the two in one app.

## Sizing a page to the card

`AppLayout.Body` is a flex **item** that is **block inside**, and neither half is optional. Together they
mean a route author never has to reason about the shell's geometry. The four page shapes each need at most
one class on the route root:

| Page shape                | What the route root needs |
| ------------------------- | ------------------------- |
| Grow and scroll (default) | nothing                   |
| Full bleed                | nothing                   |
| Contained                 | `mx-auto max-w-7xl`       |
| Fill the card             | `flex h-full flex-col`    |

Switch between all four shapes below: the shell markup never changes, only the classes on the page's own
root. The example embeds the shell rather than pinning it with `fixed inset-0`, and passes `asChild` with a
`<div>` to `AppLayout.Body`, because this docs page already owns the `main` landmark.

```tsx
import { CheckCircleIcon } from "@phosphor-icons/react/CheckCircle";
import { useState } from "react";

const pageShapes = [
	{ id: "grow", label: "Grow and scroll" },
	{ id: "full-bleed", label: "Full bleed" },
	{ id: "contained", label: "Contained" },
	{ id: "fill", label: "Fill the card" },
] as const;

type PageShape = (typeof pageShapes)[number]["id"];

/** Filler rows, so every page shape has enough content to scroll. */
function Rows({ count, label }: { count: number; label: string }) {
	return (
		<>
			{Array.from({ length: count }, (_, index) => (
				<div key={index} className="border-card-muted rounded-lg border p-4">
					<p className="text-strong text-sm font-medium">
						{label} {index + 1}
					</p>
				</div>
			))}
		</>
	);
}

/**
 * The page a route renders inside `AppLayout.Body`. Only the classes on the
 * page's own root differ between the four shapes.
 */
function Page({ shape }: { shape: PageShape }) {
	if (shape === "full-bleed") {
		return (
			// nothing on the root: the tinted background runs edge to edge, and the
			// card clips it to its own rounded corners
			<div className="bg-emerald-600/10 min-h-full">
				<div className="space-y-3 p-6">
					<Rows count={8} label="Full-bleed row" />
				</div>
			</div>
		);
	}

	if (shape === "contained") {
		return (
			// mx-auto centers at the max width because AppLayout.Body is block inside.
			// A real dashboard page clamps at max-w-7xl; max-w-md keeps the centering
			// visible at this preview's scale.
			<div className="mx-auto max-w-md space-y-3 p-6">
				<Rows count={8} label="Contained row" />
			</div>
		);
	}

	if (shape === "fill") {
		return (
			// h-full resolves against Body's definite height, so the status bar lands
			// on the card's bottom edge instead of below the fold
			<div className="flex h-full flex-col">
				<div className="border-card-muted flex shrink-0 items-center gap-3 border-b px-6 py-3">
					<p className="text-strong text-sm font-medium">Toolbar row</p>
				</div>
				<div className="relative min-h-0 flex-1 overflow-y-auto">
					<div className="space-y-3 p-6">
						<Rows count={8} label="Editor row" />
					</div>
				</div>
				<div className="border-card-muted text-muted flex shrink-0 items-center gap-2 border-t px-6 py-2 text-xs">
					<CheckCircleIcon weight="fill" className="fill-success-600 shrink-0" />
					Status bar, on the card&rsquo;s bottom edge
				</div>
			</div>
```

Why each class on `AppLayout.Body` is there, and what breaks without it:

- **`min-h-0 flex-1`** gives it a definite height, so `h-full` on a page resolves to exactly the card's
  interior. Before the toolbar moved out of the scroll container, an in-flow `sticky` header took flow space,
  so `h-full` resolved against the full content box. Every such page then overflowed by exactly the toolbar's
  height: a bottom-pinned bar hung below the fold on every load.
- **block inside, not flex.** This is the trap worth knowing about even though the part now absorbs it: if the
  page region were a flex container, **auto margins beat `align-items: stretch`**, so a route root of
  `mx-auto max-w-7xl` would shrink-to-fit, getting _narrower_ as the viewport gets _wider_. Keeping the page
  region block-level is what makes the most common page shape work at all.
- **`w-full`** states the width outright instead of leaning on the flex container's cross-axis `stretch`, so an
  `mx-auto` merged onto `Body` still leaves it full width — auto cross-axis margins would otherwise turn a
  stretched item into a shrink-to-fit one. It is no floor, though: `cx` is tailwind-merge-backed and the
  consumer's `className` wins, so a merged `w-*` replaces it outright, while a merged `max-w-*` — a separate
  conflict group — survives beside it and clamps the scrollport. Constrain the _page_ inside `Body`, not
  `Body` itself.
- **`relative`** contains absolutely-positioned page content: a toolbar floating over an editor resolves
  against the scrollport instead of escaping to `AppLayout.Root` and painting across the sidebar rail.

## Scroll restoration

`AppLayout.Body` is the scroll container, not the document, so React Router's
[`<ScrollRestoration />`](https://reactrouter.com/api/components/ScrollRestoration) has nothing to restore.
It saves `window.scrollY` and restores with `window.scrollTo`, and in this shell the window never scrolls
(`AppLayout.Root` is pinned with `fixed inset-0` and clips with `overflow-clip`). This is not new to the
shell; it has always been true of any app whose scrolling happens in an inner container.

What that means in practice:

- **Hash links work.** React Router resolves `location.hash` with `element.scrollIntoView()`, which scrolls
  the nearest scrollable ancestor, so `/endpoints#tls` scrolls the card correctly, with no extra work.
- **`document.querySelector("main").scrollTop` works**, because `Main` composes onto the scrollport. Code that
  reads or writes the page's scroll position through the `main` landmark keeps working.
- **Scroll position is _not_ reset on navigation**, and `preventScrollReset` has no effect. Navigating from a
  scrolled-down list into a new route leaves the card where it was. If that matters, reset it yourself:

Scroll a page down, then switch pages: the card returns to the top. Navigation in the example is a **fake
router**, so it can be embedded here; a real shell has no local `pathname` and keys the effect on
`useLocation().key` instead, so a back/forward entry counts as a navigation too. The ref goes on the same
element either way: this example passes `asChild` with a `<div>` because the docs page already owns the
`main` landmark, while a real shell puts the ref on `AppLayout.Body` itself.

## Landmarks

`AppLayout.Body` is the Main landmark. It renders mantle's [Main](/components/primitives/main), so it carries
`id="main"` and `tabIndex={-1}`. Pair it with a [SkipToMainLink](/components/primitives/skip-to-main-link) as
the first child of `AppLayout.Root`. Its default `targetId` matches that `id`. The framed demos on this page
do exactly this: each preview is its own document, so each owns a real `main`.

**The landmark is the scroll container, and that is what makes the skip link useful.** The element the link
focuses **is** the scrollport, so arrows, `Space`, and `PageDown` scroll the page straight away. It also keeps
the toolbar _out_ of the `main` landmark, which is what the skip link's own promise ("jump past the sidebar
and toolbar") always implied. Never move the landmark to the `AppLayout.Content` card. A keyboard user who
takes the skip link then lands on an element with no scrollable ancestor, and the keys do nothing.

Exactly one element in a document may be the Main landmark. When the shell is embedded in a page that already
owns one (a docs page, a test, a widget inside another layout), pass `asChild` and render a plain `<div>`:

```tsx
<AppLayout.Body asChild>
	<div>{/* your page content */}</div>
</AppLayout.Body>
```

The part adds its classes and `data-slot="app-layout-body"` to your element and no landmark. Every inline
example on this page does this, because the page you are reading owns the `main`.

The composition below is the canonical shell. It renders the frame, the skip link, and the content card, and
each route renders `AppLayout.Header` and `AppLayout.Body` itself (see
[One header per page](#one-header-per-page)). It is the one example here with no inline preview beside it,
deliberately: a document may contain only one `main` landmark and this docs page already owns one, and the
shell pins itself over the whole viewport with `fixed inset-0`. The framed previews on this page are single
pages, so each renders the same two parts in the shell.

```tsx

import { SkipToMainLink } from "@ngrok/mantle/skip-to-main-link";
import { Outlet } from "react-router";

					<Outlet />
```

## Accessibility

- `AppLayout.Header` renders a plain `<div>`, not a `<header>`. `AppLayout.Body` is the `main` landmark and
  the header is its sibling, so a `<header>` here would have no sectioning ancestor and would **be** the ARIA
  `banner` landmark, which a card toolbar is not. If you need one, compose your own element via `asChild`.
- `AppLayout.Notice` is deliberately **not** named Banner: it renders a plain `div` and claims no landmark.
  If the notice content needs its own semantics, put them on the content.
- `AppLayout.Body` is the `Main` landmark. Render `SkipToMainLink` first in the shell, so the landmark the
  skip link focuses is the scroll container (see [Landmarks](#landmarks)).
- The shell never scrolls; only `AppLayout.Body` does. Focus scrolling behaves like any regular scroll
  container. Both `AppLayout.Root` and `AppLayout.Content` are `overflow-clip` rather than `overflow-hidden`
  specifically so neither can become a hidden scroll container: `hidden` scrolls on focus with no scrollbar to
  scroll back, which a wide toolbar would trigger by translating the whole card (or, on the pinned frame, the
  whole window) out of view.
- **Every page renders one `AppLayout.Header`, with `Sidebar.Trigger` in `AppLayout.HeaderStart` and the
  route's trail in `AppLayout.HeaderContent`.** The sidebar can collapse at every breakpoint, and
  `Sidebar.Trigger` is the only way back from a collapsed rail or a closed mobile sheet. A page with a
  collapsible sidebar and no visible trigger is unrecoverable. [One header per page](#one-header-per-page)
  is the canonical shell that meets it.

## API Reference

Every part accepts a `ref` prop that lands on the rendered element and merges `className` deterministically
via `cx` (tailwind-merge-backed, so consumer classes win).

### AppLayout.Root

The outer frame of the shell: `bg-base relative isolate flex h-full w-full flex-col overflow-clip`. Fills
its nearest sized ancestor; merge `className="fixed inset-0"` to pin a real app shell to the viewport. The
shell itself never scrolls — only [`AppLayout.Body`](#applayoutbody) does. When the shell owns the document, render a
[SkipToMainLink](/components/primitives/skip-to-main-link) as its first child (see
[Landmarks](#landmarks)).

It is `overflow-clip`, not `overflow-hidden`, for the same reason
[`AppLayout.Content`](#applayoutcontent) is: `hidden` **is** a scroll container that paints no scrollbar, so
anything wider than the frame lets focus scroll the entire shell sideways — translating the notice, the rail,
and the card out of view with no scrollbar and no gesture to bring them back. On a frame pinned with
`fixed inset-0` that is the whole window. `clip` is not a scroll container at all.

All props from [div](https://developer.mozilla.org/en-US/docs/Web/HTML/Element/div#attributes), plus:

| Prop       | Type      | Default | Description                                                                                                           |
| ---------- | --------- | ------- | --------------------------------------------------------------------------------------------------------------------- |
| `asChild?` | `boolean` | `false` | Use the `asChild` prop to compose the `AppLayout.Root` styling onto alternative element types or your own components. |

### AppLayout.Notice

A full-window-width, vertical composition slot pinned above everything else in the shell — including any
sidebar — for app-wide messaging. Stack a rare maintenance or environment banner and a persistent account
alert bar here; each child brings its own colors and layout while the slot pushes the whole shell down.
Renders an unstyled `<div>` (`flex w-full shrink-0 flex-col`) and collapses to nothing when empty.
Deliberately not named Banner so it never reads as the ARIA `banner` landmark — it claims no landmark at
all; give the notice content its own semantics if it needs them. Optional.

All props from [div](https://developer.mozilla.org/en-US/docs/Web/HTML/Element/div#attributes), plus:

| Prop       | Type      | Default | Description                                                                                                             |
| ---------- | --------- | ------- | ----------------------------------------------------------------------------------------------------------------------- |
| `asChild?` | `boolean` | `false` | Use the `asChild` prop to compose the `AppLayout.Notice` styling onto alternative element types or your own components. |

### AppLayout.Workspace

The region where the user works — everything below the notice, laid out as a flex row of columns
(`flex min-h-0 flex-1`). Place a [`Sidebar.Nav`](/components/navigation/sidebar) (or any other rail, on
either side) beside the `AppLayout.Content` card. The `min-h-0` is what lets `AppLayout.Body` scroll instead
of the page.

It owns **no gutter**, deliberately: the card insets itself with its own margin, so a rail stays flush
against the window edge and a [collapsed icon rail](/components/navigation/sidebar#collapsing-to-the-icon-rail)
keeps its flush geometry.

All props from [div](https://developer.mozilla.org/en-US/docs/Web/HTML/Element/div#attributes), plus:

| Prop       | Type      | Default | Description                                                                                                                |
| ---------- | --------- | ------- | -------------------------------------------------------------------------------------------------------------------------- |
| `asChild?` | `boolean` | `false` | Use the `asChild` prop to compose the `AppLayout.Workspace` styling onto alternative element types or your own components. |

### AppLayout.Content

The card surface beside the sidebar:
`bg-card border-card-muted relative m-(--app-layout-card-gutter,0.5rem) flex min-w-0 flex-1 flex-col overflow-clip rounded-xl border shadow-sm`.
Holds `AppLayout.Header` and `AppLayout.Body`. In the canonical shell it wraps the route's `<Outlet />`, and the
route renders both (see [One header per page](#one-header-per-page)).

The card **does not scroll** — [`AppLayout.Body`](#applayoutbody) does. It insets itself from the window edge
and the rail with its own margin, driven by `--app-layout-card-gutter`, because the gutter has to belong to
the card: the only other element that could hold it is `AppLayout.Workspace`, which also contains the rail,
so padding there would push the sidebar off the window edge.

It is `overflow-clip`, not `overflow-hidden`, and the distinction matters: `hidden` **is** a scroll container
that paints no scrollbar, so a toolbar wider than the card lets <kbd translate="no">Tab</kbd> scroll it sideways —
translating the header and the page out of view with no scrollbar and no gesture to bring them back. `clip`
is not a scroll container at all. It also keeps a full-bleed page background from painting square corners
over the card's `rounded-xl`.

It is `relative`, so page content positioned with `absolute` resolves against the card instead of escaping to
`AppLayout.Root` and painting across the sidebar rail.

All props from [div](https://developer.mozilla.org/en-US/docs/Web/HTML/Element/div#attributes), plus:

| Prop       | Type      | Default | Description                                                                                                              |
| ---------- | --------- | ------- | ------------------------------------------------------------------------------------------------------------------------ |
| `asChild?` | `boolean` | `false` | Use the `asChild` prop to compose the `AppLayout.Content` styling onto alternative element types or your own components. |

| CSS Variable               | Default  | Description                                                                                                                                                                                                                                                             |
| -------------------------- | -------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `--app-layout-card-gutter` | `0.5rem` | The gap between the card and the window edge, the notice above it, and the rail beside it (8px). `AppLayout.Header` subtracts twice this value when deriving its height, so overriding it keeps the toolbar aligned with the sidebar header's band instead of drifting. |

### AppLayout.Header

The toolbar row at the top of the content card. Render it as `AppLayout.Content`'s **first child**
(`border-card-muted flex h-14 shrink-0 items-center gap-2 border-b px-4`), and compose its three slots in
order: [`AppLayout.HeaderStart`](#applayoutheaderstart) for the
[`Sidebar.Trigger`](/components/navigation/sidebar#sidebartrigger),
[`AppLayout.HeaderContent`](#applayoutheadercontent) for the [Breadcrumb](/components/navigation/breadcrumb)
trail, and [`AppLayout.HeaderActions`](#applayoutheaderactions) for the page's actions. The slots carry the
flex, so no call site sets `flex-1`, `min-w-0`, `shrink-0`, or `ml-auto` itself. In the canonical shell, each route renders it (see
[One header per page](#one-header-per-page)).

It is **pinned by construction, not by `sticky`**: as a `shrink-0` flex sibling _outside_ the scrolling
`AppLayout.Body`, it cannot scroll away, cannot be overlapped by a page's own `sticky top-0`, does not
translate sideways when the page scrolls horizontally, and does not steal height from a page asking for
`h-full`.

Renders a `<div>`, not a `<header>`. `AppLayout.Body` is the `main` landmark and this row is its sibling, so a
`<header>` here would have no sectioning ancestor and would _be_ the ARIA `banner` landmark, which a card
toolbar is not.
Optional standalone; effectively required once a `Sidebar` is composed (see
[Accessibility](#accessibility)).

**Sidebar alignment is an invariant, not a coincidence:** standalone, the toolbar is `h-14`. When the shell
contains a `Sidebar.Header` (detected with `:has()` from `AppLayout.Root`), the toolbar instead derives its
height from the sidebar's public `--sidebar-header-height` token as
`calc(var(--sidebar-header-height, 4.5rem) - 2 * var(--app-layout-card-gutter, 0.5rem) - 2px)` — subtracting
twice the card gutter and twice the card's hairline border — which keeps this toolbar's vertical center on
the band that token names, for any band height. The band belongs to the
[sidebar header's first row](/components/navigation/sidebar#sidebarheader), so a header that stacks a second
row grows downward while this toolbar keeps matching the switcher row alone. Override
`--sidebar-header-height` on a common ancestor (e.g. `AppLayout.Root`'s `className`) and both rows move
together.

> [!NOTE]
> The alignment is a **desktop-only** coupling. Below the sidebar's `mobileBreakpoint` the sidebar renders
> inside a `Sheet` portaled to `document.body` — outside the shell subtree — so the `:has()` selector stops
> matching and this toolbar falls back to its standalone `h-14`. That is a 2px change (54px → 56px) applied
> after hydration, since the server renders desktop-first. There is nothing to align to on mobile anyway, but
> it explains the 2px if you are diffing layout across breakpoints.

All props from [div](https://developer.mozilla.org/en-US/docs/Web/HTML/Element/div#attributes), plus:

| Prop       | Type      | Default | Description                                                                                                                                                                                 |
| ---------- | --------- | ------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `asChild?` | `boolean` | `false` | Use the `asChild` prop to compose the `AppLayout.Header` styling onto alternative element types (e.g. a `<header>` when the shell does not own the `main` landmark) or your own components. |

| CSS Variable               | Default  | Description                                                                                                                                                                                                                                                                        |
| -------------------------- | -------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `--sidebar-header-height`  | `4.5rem` | Read (not set) by `AppLayout.Header` when the shell contains a [`Sidebar.Header`](/components/navigation/sidebar#sidebarheader), which owns the token — the band its first row sits on. Set it on a common ancestor of both (e.g. `AppLayout.Root`) so the two rows move together. |
| `--app-layout-card-gutter` | `0.5rem` | Read (not set) by `AppLayout.Header`; owned by [`AppLayout.Content`](#applayoutcontent). The derived height subtracts twice its value, so changing the card gutter keeps the two rows aligned.                                                                                     |

### AppLayout.Body

The page region, and the shell's **only** scroll container:
`scrollbar relative min-h-0 w-full flex-1 overflow-y-auto overscroll-none`. Render it after
`AppLayout.Header` inside `AppLayout.Content`. In the canonical shell the route renders both, with
the page content as the body's children (see [One header per page](#one-header-per-page)).

It renders mantle's [Main](/components/primitives/main) landmark: `<main id="main" tabIndex={-1}>` with
`data-slot="app-layout-body main"`, so a [SkipToMainLink](/components/primitives/skip-to-main-link) lands on
the scroll container (see [Landmarks](#landmarks)). `id` and `tabIndex` are not props. When the document
already owns a `main`, pass `asChild` and render a `<div>`. The part then adds its classes and
`data-slot="app-layout-body"` to your element and no landmark.

Every class on it has a job; see [Sizing a page to the card](#sizing-a-page-to-the-card) for what each
one buys a route author, and [Scroll restoration](#scroll-restoration) for what an inner scrollport means for
your router.

All props from [main](https://developer.mozilla.org/en-US/docs/Web/HTML/Element/main#attributes) except `id` and `tabIndex`, plus:

| Prop       | Type      | Default | Description                                                                                                                                                                                         |
| ---------- | --------- | ------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `asChild?` | `boolean` | `false` | Use the `asChild` prop to compose the `AppLayout.Body` styling onto alternative element types (a `<div>` when the document already owns the `main` landmark, a `<section>`) or your own components. |

### There is no AppLayout.Footer

Deliberately. A bar pinned to the bottom of the card is almost always a **page's** bar — an editor's validity
line, a save bar, a selection count — and a route rendering through an `<Outlet />` inside `AppLayout.Body`
could never reach a shell-level part, because it would be a sibling of the region the route renders into.

Pin it inside `AppLayout.Body` instead:
[Pinning a footer to the card](#pinning-a-footer-to-the-card).
