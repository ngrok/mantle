# Scaffold a new mantle component

Scaffold a new component named `$ARGUMENTS` in the mantle design system. If no name is provided, ask the user for a component name.

**[COMPONENT_SPEC.md](../../COMPONENT_SPEC.md) is the normative standard — read it before writing anything.** This workflow is only the order of operations; every rule lives in the spec. Where the two appear to disagree, the spec governs: report the mismatch, do not edit this file mid-task.

## 0. Normalize the component name

Accept any of these formats and derive the three canonical forms from [COMPONENT_SPEC.md §2.2](../../COMPONENT_SPEC.md#22-naming):

| Input          | `<component-name>` | `<ComponentName>` | `<Display Name>` |
| -------------- | ------------------ | ----------------- | ---------------- |
| `ButtonGroup`  | `button-group`     | `ButtonGroup`     | `Button Group`   |
| `Button Group` | `button-group`     | `ButtonGroup`     | `Button Group`   |
| `button group` | `button-group`     | `ButtonGroup`     | `Button Group`   |
| `button-group` | `button-group`     | `ButtonGroup`     | `Button Group`   |

Use these three forms consistently in every step below.

## 1. Design gate — before any code

Work [COMPONENT_SPEC.md §1](../../COMPONENT_SPEC.md#1-before-you-scaffold) with the user and raise conflicts **now**, not at review time. Every question there is expensive to change after release:

- §1.1 — does it duplicate an existing component's user intent?
- §1.2 — should any of it stay module-internal? Is it public, preview, or a layout?
- §1.3 — is the outermost part `Root`, and is every part named for the DOM/ARIA it emits?
- §1.4 — does any proposed name borrow an ARIA pattern word it has not earned?
- §1.5 — composition or data-driven?
- §1.6 / §1.7 — are invalid states unrepresentable, and does the API avoid every forbidden shape?

Then ask the user:

> Is `<ComponentName>` a compound component (a POJO namespace with multiple parts) or a simple single-element component?

If compound, follow up:

> What are the parts, and how do they nest? (e.g. `Root > Header > Title + Body + Footer`)

Build the ASCII composition tree from that answer — it is the single source of truth for the namespace JSDoc (§4.2) and the docs page's `## Composition` section (§7.2 item 5), and the two must match exactly.

If the component wraps a third-party primitive, add the dependency first with an exact pinned version: `pnpm -w add -E <package> -F @ngrok/mantle`. Add it to `pnpm-workspace.yaml`'s `catalog:` first if it will be shared across packages.

## 2. Write the component

Create `packages/mantle/src/components/<component-name>/` — or the family directory, per §2.2 — with the implementation, `index.ts`, and a colocated test file.

Follow [§3](../../COMPONENT_SPEC.md#3-implementation-rules) for the implementation (`"use client"`, `.js` imports, `ComponentProps`-based props, `data-slot` on every part, `asChild` on every DOM-rendering part, compound namespace shape, invariants, accessibility, SSR), [§4](../../COMPONENT_SPEC.md#4-jsdoc) for JSDoc, [§5](../../COMPONENT_SPEC.md#5-css-variables-are-api) and [§6](../../COMPONENT_SPEC.md#6-data-attributes-are-api) for public CSS variables and data attributes, and [§8](../../COMPONENT_SPEC.md#8-tests) for tests.

`index.ts` re-exports from `./<component-name>.js`. If the component surfaces helpers from a wrapped library that consumers need to compose it (pattern constants, type predicates), re-export those too — only the ones consumers need:

```ts
export { OtpInput, REGEXP_ONLY_CHARS, REGEXP_ONLY_DIGITS } from "./otp-input.js";
```

Copy shape from the exemplars named at the end of the spec — and heed the gaps listed there.

## 3. Write the docs page

Create the page at the path for its kind ([§7.1](../../COMPONENT_SPEC.md#71-page-kinds)) and follow [§7.2](../../COMPONENT_SPEC.md#72-required-structure-in-order)'s required sections in order, [§7.3](../../COMPONENT_SPEC.md#73-examples-must-be-live-and-complete) for examples, and [§7.4](../../COMPONENT_SPEC.md#74-prose-rules) for prose.

Every runnable example must be **live** and **complete** — no fragments, no `…` placeholders, no undefined identifiers. The API reference gets one `### <ComponentName>.<Part>` subsection per part with its props table, plus CSS-variable and data-attribute tables where applicable.

## 4. Wire it up

Per [§2](../../COMPONENT_SPEC.md#2-what-a-component-must-ship):

1. `packages/mantle/package.json` — the `"./<component-name>"` export entry, alphabetical (§2.3).
2. `apps/www/app/routes.ts` — `...docRoute("components/<category>/<component-name>"),` alphabetical (§2.4).
3. `apps/www/app/components/navigation-data.ts` — `componentsByCategory` + `prodReadyComponentRouteLookup` for a stable component, the three preview lookups for a preview component, or the layout arrays for a layout. Add `componentImportPathOverrides` if the docs slug is not the export key (§2.4).
4. The conditional build-config edits in §2.1's second table, if they apply — `INTERNAL_CHUNKS_BY_COMPONENT` in particular, since missing it ships an unstyled component with every check green.

Pick the category from the nine in §2.4 (`Actions`, `Charts`, `Data Display`, `Feedback`, `Forms`, `Navigation`, `Overlays`, `Primitives`, `Structure`) and use its slug from `componentCategorySlugs`. Ask the user if genuinely ambiguous.

## 5. Verify and changeset

Run all five commands in [§9](../../COMPONENT_SPEC.md#9-verification), then commit the generated files it names (`components-surface.json`, `mantle-component-name.ts`).

Add a `minor` changeset for `@ngrok/mantle` written as release notes for consumers, per [§2.5](../../COMPONENT_SPEC.md#25-changesets).

## 6. Self-review

Work [COMPONENT_SPEC.md §11](../../COMPONENT_SPEC.md#11-review-checklist) against your diff before reporting completion. Report anything you could not satisfy rather than leaving it silent.
