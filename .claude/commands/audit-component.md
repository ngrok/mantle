# Audit a mantle component

Audit the component named `$ARGUMENTS` against [COMPONENT_SPEC.md](../../COMPONENT_SPEC.md) and fix the discrepancies that are safe to fix. This is the mirror of `/scaffold-component` — the same standard, applied to an existing component.

**The spec is the standard; this workflow is only how it gets checked.** Where the two appear to disagree, the spec governs: report the mismatch, do not edit this file mid-task.

Read [Scope and status](../../COMPONENT_SPEC.md#scope-and-status) first, and honor it. Much of the library predates parts of the spec. An audit **reports** the gap — it does not open a library-wide migration inside an unrelated PR, and it never rewrites a shipped API to satisfy a rule without the author's decision.

If `$ARGUMENTS` is empty or `all`, apply the audit to every component directory that has a `packages/mantle/package.json` export, and tell the user up front roughly how many findings you expect to be author-judgment rather than auto-fixable — a full sweep of a pre-spec library produces a lot of the former.

## 0. Normalize the component name

Accept PascalCase, Title Case, lowercase, or kebab-case, and derive `<component-name>`, `<ComponentName>`, and `<Display Name>` per [§2.2](../../COMPONENT_SPEC.md#22-naming).

Resolve the input against the real layout before giving up: a component may live in a **family directory** (`icon-button` in `button/`, `password-input` in `input/`, `progress-bar` and `progress-donut` in `progress/`), so the absence of a `<component-name>/` directory is not proof the component does not exist. Only stop and report "no such component" once neither a directory nor a family-directory file matches.

## 1. Classify

Follow [§10.1](../../COMPONENT_SPEC.md#101-classify): read every non-test `.tsx` for the component, decide compound vs simple, detect `asChild` support, and confirm the directory is in scope (skip export-less directories — today only `chart` — and `*/primitive.tsx`).

## 2. Check

Walk [§10.2](../../COMPONENT_SPEC.md#102-check)'s table in order and record every violation with a `file:line`:

- **Surface & API** — §1.1–§1.7
- **Implementation** — §3
- **JSDoc** — §4, plus §5.2 and §6
- **Docs page** — §7
- **Wiring** — §2
- **Tests** — §8

Two checks are worth calling out because they are the ones most often missed and the spec's own review pass found them absent library-wide: every public CSS variable must appear in **both** the JSDoc and the docs-page API reference (§5.2), and every `data-*` the component stamps for styling or coordination must appear in both as well (§6).

## 3. Fix

Apply the auto-fixable items in [§10.3](../../COMPONENT_SPEC.md#103-fix); report the author-judgment items and wait.

The two hard rules there:

- **Adding a `package.json` export is never an auto-fix.** Publishing is irreversible, and an export-less directory is usually internal on purpose.
- **Never auto-fix a naming violation by changing the markup.** Adding an ARIA role, a keyboard handler, or `tabIndex` to make an unearned pattern word honest changes runtime behavior and accessibility semantics to preserve a name that should change instead.

## 4. Report, verify, changeset

Per [§10.4](../../COMPONENT_SPEC.md#104-report): group findings by area, mark each auto-fixable or author-judgment, apply the auto-fixable ones, then run all five commands in [§9](../../COMPONENT_SPEC.md#9-verification) — including the unscoped `pnpm -w run test`, since the `@app/www` suite is what guards the JSDoc and manifest surface an audit most often changes. Commit the generated files §9 names.

Changeset per [§2.5](../../COMPONENT_SPEC.md#25-changesets): `patch` for JSDoc/comment-only changes to `packages/mantle`, none if only `apps/www/app/docs/**`, `navigation-data.ts`, or `routes.ts` changed.
